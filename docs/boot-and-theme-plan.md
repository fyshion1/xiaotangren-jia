# 启动动画 + 主题设计 —— 调研与方案

> 本文只做**调研 + 方案**，不含实现。要动手时，实现口径写进《项目要求.txt》，本文只留一句「已落地 → §X」。
>
> **当前设计方向以第 14 节为准**。前面的调研保留为历史资料；“全局科技感”“只换五个强调色”“所有角色共用烘焙坊底色”等早期提案，不再作为当前视觉约束。
>
> **角色参考校准见第 15 节**。当前阶段只读图、读已有界面并提出美化方案，不改产品代码、不实施 demo；第 14 节结尾的 demo 排期暂缓。
>
> 调研对象是两个 DSH（DeepSeek Harness）插件仓库 —— 它们跟小糖人之家没有代码关系，
> 只是**「在应用起来之前先放一层启动画面」**这件事上目前最完整的两个实现。学的机制，不是抄的代码。

---

## 0. 一句话结论

两个仓库真正的价值不是那几段 mp4，而是**一个机制**：

> 在 `<head>` 里塞一段**解析阻塞的、不依赖框架的**脚本，
> 在 shell 挂载**之前**就把启动层画出来，等「内核就绪」再溶解交接。

小糖人之家现在 [frontend/index.html](../frontend/index.html) 是个几行的空壳，
`#root` 挂载前屏幕上什么都没有 —— 这正是"能加启动屏"的前提条件，也是现在首屏白闪的来源。

## 1. 两个参考仓库在做什么

### 1.1 `lxj5820/dsh-boot-animation`（原版，21 commits，208★）

Host 侧 + Client 侧两半：

- **Host**（`entry.js`，656 行）：注册设置项、注册 `clips.json` 资源路由（带 HTTP Range）、
  用 `webserver/index-inject` hook 往 `<head>` 里注入脚本。
- **注入脚本**（`src/boot-screen.js`，1344 行）：无框架，必须在 shell 之前跑完。
  读 `window.__DSH_BOOT_ANIM_CFG__`，并从内核的 `--dsh-boot-arc` CSS 变量拿**真实**启动进度。
- **Client**（`client.js`）：设置卡片 + 交接信号。

它暴露的问题（也正是第二个仓库存在的理由）：

| 坑 | 后果 |
|---|---|
| 设置卡挂在 `plugins.item` | 那是官方插件用的 slot，卡片**从来没出现过** |
| 依赖 `schemastery` + `.volatile()` | 设置项**静默失效**，改配置没反应 |
| 依赖 peerDependencies | 静态 `import` 缺 peer 会**连累整个插件加载失败** |
| `files` 白名单漏掉 `tools/` | 安装脚本自检失败，**误判后回滚** |
| `install.ps1` 靠本地端口判断成功 | 判断依据本身不可靠 |

### 1.2 `GA17-LHY/dsh-boot-splash`（桌面端重写版，11 commits）

同样的效果，重写了四处：

| 修复 | 做法 |
|---|---|
| 设置卡挂对 slot | `slots.register({name: 'plugins.bundle.config', key: '<pkg>'}, Component)`，且必须在 `slots.inject(slotName, cb)` **内部**注册 |
| 配置存储 | 纯 JSON 存 `$DSH_HOME/boot-splash.json`，**原子写**（临时文件 + rename），只做合并 —— 完全绕开 schemastery / `.volatile()` |
| 自包含 | **零 dependency、零 peerDependencies**，无硬编码路径（`import.meta.url` / `DSH_HOME` / `os.homedir()`），素材随包分发 |
| 写入端点 | 要求 `x-boot-splash-write: 1` header + loopback Origin；路由**精确匹配**（除 `/clip` 前缀），否则会吞掉客户端 bundle |

它还带了一个 73 条断言的 `tests/verify.mjs`，和一个纯 ASCII 的 PowerShell 校验器 ——
因为 **Windows PowerShell 5.1 会按系统 ANSI 解码无 BOM 的文件**，把中文字节当字符串终止符吞掉。

### 1.3 时序机制（`src/boot-screen.js` 里的常量，这是最值得抄的部分）

```js
var HOLD_MS  = cfg.holdMs ?? 15000        // 兜底超时：到点无条件进入
var FADE_MS  = cfg.fadeMs ?? 2000         // 限制在 300–5000
var ENTER_MODE = 'tail' | 'end' | 'click' // 进场景的时机
var TAIL_MIN_MS = FADE_MS * 2             // 剩余不足 2×FADE 就提前溶解
```

关键设计：

- **进度是真的**，不是假动画条 —— 从内核的 CSS 变量读，读不到就写"不确定"，**绝不伪造百分比和时间**。
- **每一帧都判一次**：`duration - currentTime <= FADE_MS` 就溶解。
  且在 `requestAnimationFrame` **和** `timeupdate` 两处都挂 —— 因为后台标签页会节流 rAF。
- **层层封顶**：manifest 10s、无画面片段 6s、未知时长 20s、框架未就绪 15s 警告。
  任何一个环节卡住都不能把人困在启动屏里。
- **Esc / Space / Enter 永远跳过。**

### 1.4 视频素材的硬约束（如果走视频路线）

- 16:9，时长 ≈ 你**希望用户等多久**（8–15 秒），不是越长越好
- **`moov` box 必须在文件最前面** —— 否则浏览器要下完整个文件才能显示第一帧。
  这是"黑屏启动"的头号原因。修法是 faststart 重写（调整 `stco`/`co64` 偏移表，不需要 ffmpeg）
- AAC 音轨，720p 够用，画面上**不要有文字 / 水印**（否则跟后面的 UI 打架）
- **HTTP 缓存语义**：完整响应用 `no-cache + ETag`（可重新验证的 304）；
  **206 Range 响应必须 `no-store`** —— 上游踩过一次 `immutable` 的坑，
  截断的片段被缓存住，普通刷新黑屏、硬刷新正常，排查了很久
- **Chromium 自动播放策略**：没有用户手势不能有声自动播放。
  默认只能是"静音启动 + 首次点击解锁"，页面改不了 `--autoplay-policy`

| # | 参考项目的做法 | 本项目的对应位置 |

| 1 | 解析阻塞的 `<head>` 启动层 | [frontend/index.html](../frontend/index.html) —— 现在是个几行的空壳，`#root` 之前可以插任何东西 |
| 2 | 无框架、无 import、纯 inline | 同上。启动层**不能**依赖 React/Tailwind，否则它自己也白闪 |
| 3 | 读真实就绪状态 | [App.tsx:187](../frontend/src/App.tsx#L187) 有现成的 `charsReady` —— 角色卡没到就写"还在叫她们起床" |
| 4 | 全部超时封顶 + 可跳过 | 新增。任何一档卡住都不能困住用户 |
| 5 | 主题用 CSS 变量 | [index.css](../frontend/src/index.css) 已经是了 —— **tsx 里 0 处硬编码粉 hex**，全走 `var(--pink*)` |
| 6 | 素材从数据里读，不硬编码 | 角色真源在 SQLite 的 `characters` 表（`emoji` / `avatar` / `portrait`），启动屏应该**读角色卡生成** |

第 5 条是这次调研最让人高兴的发现：**换主题的成本极低**，
因为整个前端没有任何一处绕开变量写死颜色。

### 唯一的例外

`.t1`–`.t6`（画廊占位渐变）在 [index.css:353-364](../frontend/src/index.css#L353-L364) 里
写死了 12 组 hex（6 亮 + 6 暗）。**要走多主题，这 12 行必须先变量化**，否则画廊格子会跟主题打架。

## 3. 本项目现状盘点

**已有的**：

- 主题系统 = `.dark` class 切换 + `:root` / `.dark` 两套 `--*` 自定义属性
- 色板 = 一套 Nekopara 暖色烘焙坊：奶油白 / 暖棕 / 可可底，草莓粉主色，薄荷 + 淡蓝点缀
- accent 变量：`--pink` `--pink-deep` `--pink-soft` `--mint` `--sky`
- `localStorage['xtr.theme']` + 回退 `matchMedia('(prefers-color-scheme: dark)')`
- 入口：`index.html` → `main.tsx` → `App.tsx`

**没有的**：

- 启动屏 / 闪屏 —— 一点都没有
- 多主题（只有明暗两档）
- 任何形式的角色专属视觉

**素材现实**：

| 角色 | 头像 | 立绘 | 备注 |
|---|---|---|---|
| 大诗音 🌸 | ✅ 2048² | ✅ 1600×2848 | 有第二形态（紫发） |
| 小诗音 🎒 | ✅ 2048² | ✅ 1080×1920 | 有第二形态（小偶像） |
| 小白 🐾 | ✅ 2048² | ✅ 577×1024 | 单形态 |
| 小红薯头 🍠 | ❌ | ❌ | **只有 emoji，没有任何图** |
| 大老大 🐻 / 汐子 🌊 | ❌ | ❌ | 私人身份，同样只有 emoji |

`gallery/orig/` 里有 3 个用户自己放的 mp4（1.3–3.7MB）—— 但那是画廊内容，**不是启动素材**。

## 4. 方案

分三层，互相独立，可以只做其中一层。

### 4.1 A 层：启动层（改 `index.html` + 一个 CSS 块）

结构照搬参考项目，但**不做插件**（我们不是 DSH，没有插件系统）：

```
frontend/index.html
  <head>
    <style>  启动层的全部样式，内联，零依赖
    <script> 画启动层 + 超时 + 跳过，内联，零依赖
  <body>
    <div id="xtr-boot">  ← 静态标记，浏览器解析到就画
    <div id="root">
```

- **不 import 任何东西**，所以它先于 React/Tailwind 生效，没有白闪
- **配色读 CSS 变量**，所以自动跟随明暗、也能跟随主题
- **读 SQLite 角色卡**：`fetch('/api/characters')` —— 拿 `emoji` / `avatar` / `portrait` / `activeFormId`
- **交接**：`charsReady` 为真 + 最短展示时间已过 → 溶解；参考项目的 `splash-exit` 那套
- **封顶**：角色卡 3s 拿不到就先进去（并写"没读到"，不伪造）；15s 硬超时；任意键跳过
- 溶解后 `#xtr-boot` 从 DOM 里摘掉，不留节点

**为什么不做成"读真实启动进度"的那套**：DSH 是 Electron 内核 + 插件加载，有几秒真实启动时间可以展示。
小糖人之家是 Vite + FastAPI，首屏基本是**瞬时**的 —— 硬塞一个假进度条反而假。
所以这里的定位应该改一下：**不是"遮住漫长的启动"，是"给每次进入一个仪式感"**。
这意味着它应该短（2–3 秒）、可跳过、且不挡事。

### 4.2 B 层：主题（改 `index.css` 顶部 + 极少量 tsx）

**不新增布局，不动 §28 冻结的手机端。** 只加一层与 dark 正交的维度：

```html
<html class="dark" data-accent="dashiyin">
```

`data-accent` 只覆盖 5 个 accent 变量（`--pink` `--pink-deep` `--pink-soft` `--mint` `--sky`），
底色 / 边框 / 文字**一律不动** —— 这样任何一个主题都不会破坏可读性，也不需要重做排版。

```
:root            → 现有 Nekopara 暖色（默认，保持不变）
[data-accent=…]  → 只改 5 个 accent，且要写亮/暗两套
```

同一套机制天然支持「跟随当前角色」：聊谁就换谁的色。这是**零布局改动**的精致化。

前置工作：把 `.t1`–`.t6` 的 12 组 hex 改成变量（§2 唯一例外）。

### 4.3 C 层：数据纪律（不写代码，只是口径）

抄参考项目的态度，写进实现口径：

- 进度 / 时间 / 百分比 —— **读不到就写"不确定"**，绝不伪造
- 每一个等待环节都有**上限**，任何一环卡住都要能进得去
- 启动层**不能是**进入应用的必经之路：跳过键永远在，且不需要提示

## 5. 每位小糖人的启动设计

原则：**从 [角色设定.md](../角色设定.md) 里长出来，不是随便配个颜色。**
每人一个色 + 一个动作 + 一句她自己会说的话。

| 角色 | 色（accent） | 动作 / 画面 | 文案 | 依据 |
|---|---|---|---|---|
| 🌸 大诗音 | 草莓粉 + 奶油 | 烤箱暖光渐亮 → 热气上浮、可可冒泡 | 「热可可就快好了哦，先进来坐～」 | 烘焙、热可可、暖烘烘 |
| 🎒 小诗音 | 日落橙粉 + 琥珀 | 战术 HUD 自检：扫描线过一遍、方框锁定、呆毛雷达竖起 | 「战术报告：本副官已经把大老大的后背彻底锁死啦！」 | 战术副官、呆毛像雷达、口头禅 |
| 🐾 小白 | 雪白 + 天蓝 | 最柔的一个：白光晕开、猫耳轻动、咕噜声波一圈圈散 | 「喵呜～大老大，进来听小白的咕噜咕噜声喵～」 | 雪白、咕噜降噪、软萌 |
| 🍠 小红薯头 | 红薯橙 | 最闹的一个：弹跳、摇头晃脑、拉批拉批 | 「拉——批——！拉批拉批拉批！」 | 高频摇头晃脑、口头禅 |

**第二形态也跟着走**（§17）：大诗音切紫发 → 紫罗兰色；小诗音切小偶像 → 粉金渐变。
因为形态是 `activeFormId` 里的数据，启动屏读一下就能跟。

**⚠ 小红薯头没有素材。** 她 `avatar` / `portrait` 都是 `None`。
她的启动画面**只能**用 emoji 🍠 或者纯 CSS 图形（圆滚滚的橙色团子 + 高频晃头其实是能做到的），
或者等你给她出图。**这一条我不会自己编素材。**

## 6. 要拍板的事

在写任何代码之前，这几件必须你定 —— 我猜不了：

1. **启动层做成什么**
   - (a) 视频剪辑 —— 需要你先出/找到 4 段 mp4（参考项目那两段是豆包 seedance 生成的）
   - (b) 立绘 + CSS 动效 —— 用现有立绘，立刻能做，不需要新素材
   - (c) 纯 CSS 构图 —— 最轻，不依赖任何图片，小红薯头也能有
   - (d) Live2D —— 记忆里你之前说这个"暂缓，先讨论"

2. **什么时候放谁的**
   - 每次加载随机一位？按固定顺序轮？只在你打开她的介绍页 / 聊天时？
   - 还是就固定放"家里的门面"（大诗音）？

3. **主题做到哪一步**
   - (a) 只打磨现在这一套 Nekopara 暖色（把明暗两档做细）
   - (b) 加「按角色换 accent」——只换 5 个变量，零布局改动
   - (c) 更大：整套换肤（那就要动布局，得先谈）

4. **小红薯头（以及大老大 / 汐子）的素材怎么办**
   - 等我出图 / 你自己给 / 就先用 emoji

5. **手机上要不要有**
   - 手机端布局 §28 是冻结的。启动层是覆盖层、不进布局，**默认不影响**；
     但手机端首屏本来就快，你要不要也在手机上放？

## 7. 明确不做的事

- **不动 §28 冻结的手机端布局**。启动层是覆盖层，不参与布局。
- **不给 `body` 加 `overflow: hidden`**（§19.23 的坑）。
- **不伪造进度 / 时间 / 百分比**。
- **不编角色素材**。没有图就写"没有图"。
- **不把启动层做成必经之路**。

### 看案例时的检查表

- **缩略图是否一眼认人**：去掉文字后，仍能凭轮廓、道具或色块认出角色。
- **主色是否少而准**：每位角色最多 1 个主色、1 个辅助色、1 个中性底色；不要用五种高饱和渐变。
- **动效是否有动词**：烤、扫描、呼吸、弹跳、漂浮，比“泛光 + 粒子”更容易留下记忆。
- **文字是否像签名**：一行角色口头禅或状态短句即可，避免在启动层放功能解释。
- **静止帧是否成立**：动画暂停时画面也要好看，说明构图本身可靠。
- **交接是否安静**：启动层退出只做一次 300–500ms 的淡出，应用本体不要再叠第二层过渡。

### 面向本项目的推荐方向

先做一套“**家居舞台 + 角色签名**”系统：底层固定为低对比的奶油/可可空间，角色色只出现在细线、按钮、状态点和启动层的一处光源；每次启动随机或按当前聊天角色展示 2 秒左右的短动作。这样既保留 Nekopara 的温度，又获得动画官网常见的留白、版式和识别度。视频素材可以后置，现有立绘与 CSS 已足够验证风格。

### 推荐的融合方式

| 汐子 | 浪漫、奔放、自由，天空与大海，蓝色 | 天青、海蓝、蓝绿，白色浪光；可试少量落日珊瑚作对比，不局限深蓝夜色 | 开阔横向视野、天空渐层、水面折射、流动弧线和风的方向；允许角色轮廓越出封面边界 | 藤ちょこ的空间色彩、torino 的冷暖光、Hiten 的空气感，做成海天主题而非科幻主题 |

### 体系与边界

- **保持统一的阅读与操作秩序**：字体层级、常用控件语义、导航位置、正文密度保持一致；角色差异可体现在封面构图、背景光色、材质、图形与启动动作，不能只换按钮颜色。
- **装饰集中在视觉舞台**：启动、介绍页封面、小窝主题、占星卡面可更丰富；聊天正文和输入区域保留安静、稳定、可读的表面。原研哉只借鉴留白与主次，不再用空白卡片代替视觉设计。
- **穆夏专用于占星卡面候选**，不将传统花饰铺成全局主题；科技风只服务小诗音相应场景。
- **视觉场景不等同新增角色形态**：现有小诗音只有基础技术宅与小偶像两套；“日常甜美 / 专业科幻”暂记录为视觉场景，不擅自新增第三形态，也不改角色性格与提示词。
- **汐子是私人身份**：按私人空间的身份数据接入主题，不将其擅自改成普通角色或加入聊天阵容。
- 小红薯头、大老大的细化方向本轮未指定，保留待定；不根据其他角色推定他们的主题。
- 现有第一轮 demo 的奶油烘焙与白色科技已否定；夜间星轨只保留配色参考，不意味着该模板构图获得认可。

下一轮应先用同一类真实页面做静态视觉比较，优先验证“大诗音日常 vs 紫发”的差异，再扩展小诗音、小白与汐子。正式接入前完成素材清点和亮暗模式可读性验证；手机布局约束继续有效。

## 15. 读图后校准：三位角色气质与现有界面的美化方案

### 范围与证据

本轮逐张查看 `reference_picture/角色参考` 的四张图：标准大诗音、大诗音标准三视图、小诗音、小白；以及 `ui-reference` 下七张 UI 参考。另阅读《角色设定.md》、现有 App / HomeView / CharacterProfileCard / PortraitCarousel / ChatView / NestView 的相关结构与主题 CSS。参考截图是审美和结构参考，不代表当前项目运行截图；下面针对现有页面的判断来自组件和样式阅读，未宣称完成实时浏览器验收。

用户明确要求项目只做美化方案：本轮不改产品代码、不改业务、不安装工具、不改旧 demo。此前接入 React Grab 是更早授权的工作，本轮不撤销也不追加。只更新本方案文档。

### 大诗音：安静的迎接，柔亮而有分量

**图中可见**：玫瑰粉长发和发饰、珍珠白围裙与长袜、整齐的荷叶边、小面积金色扣件；胸前是金边蓝色宝石。站姿舒展、双手自然向外，表情柔和，长发与后方飘带形成延伸曲线。三视图显示背面大蝴蝶结和长飘带，也是重要的角色符号。标准图偏细腻的立体渲染，不能默认与所有二次元平涂素材天然一致。

**结合用户定位的理解**：成熟和包容主要靠姿态、比例、柔和目光以及材质分量表达。粉色很丰富，但有大面积白色承托，细节既甜又整齐。可用一句话概括为“她已经准备好迎接你，动作从容，不急着吸引注意”。

**美化提案**：

- 日常主视觉用玫瑰粉、珍珠白、很浅的中性玫瑰灰；蓝宝石色作为小面积识别点，金色只给少量精细节点。既不全页暖黄，也不把粉色压成灰棕。
- 角色介绍中优先保证脸、头饰、发丝和蓝色宝石的识别；全身图用于立绘展示，头像及聊天缩略图单独设想脸部裁切。不要用同一裁切强行适配所有尺寸。
- 从飘带取长曲线，从服装取细窄滚边与有节奏的间距。蕾丝与玫瑰可用于一两个角部，信息项不逐个加花边。
- 日常启动可让柔和光源先显出人物轮廓，再落到目光和宝石亮点；动作幅度小。烘焙是生活语境，可作局部道具，不必每页都有烤箱。
- 紫发形态延续同一人的目光与从容，变化放在环境光、空间与撞色上，避免突然变成完全不同的角色。本目录没有紫发参考，暂不能确定其服饰、配饰和具体发色。

### 小诗音：向你伸手，轻盈而有冲劲

**图中可见**：暖金 / 浅棕色双马尾大幅向上展开，橙金眼睛、眨眼与笑容、两只向观者伸出的手；橙红服装配白色毛边，黑色束腰形成清楚的深色中心，点缀绿丝带。亮点和细长金色轨迹围绕人物，形成明显上升和旋转动势。

**结合用户定位的理解**：比大诗音更主动、更外放，亲近感来自“邀请你加入”。这张是圣诞场景，红绿和节日文案不能当成永久身份标记；参考图发色也与档案里的“日落橙粉”不完全相同，应分开记录，不能擅自改人设。

**美化提案**：

- 日常从暖桃、杏橙、亮白中提取轻快配色，保留少量深色压住结构；避免所有界面元素都浅粉，导致失去活力和焦点。
- 图形可提取双马尾上扬弧线、蝴蝶结、呆毛和短光轨。缩略图优先眼睛和表情；封面留出头发的运动空间。
- 偶像场景加强橙红、金色与舞台对比，沿伸手与发丝方向组织构图；动效强调一次轻快的展开，而非持续闪烁。
- 科技场景保留她的暖色识别点与主动性，以准确的对齐、功能分区、清晰读数和利落转场表达专业。无需照搬节庆服，也不把冷蓝当作唯一科幻颜色。
- 日常、偶像、科技仍属于同一角色；科技作为视觉场景处理，当前不新增第三个业务形态。

### 小白：靠近的温度，暖白与绒感

**图中可见**：奶白 / 浅灰发色中有浅粉色过渡，粉紫眼睛、绯红脸颊、耳内暖粉、蓬松耳毛和尾巴；抱着白色毛绒玩偶，穿有针织纹理的浅茶粉衣服。背景是暖木地板、布艺沙发与软垫。画面是近距离、略俯视的构图，人物看向观者。

**结合用户定位的理解**：软萌来自绒毛、针织、贴近的距离和抬头目光。她并非没有表情的冷白角色；图里有很明确的温度、害羞和活泼回应。甘城作为软萌参考继续保留，但具体色彩以这张角色图为重要校准。

**美化提案**：

- 暖白为主体，浅茶粉与粉紫点色；雾蓝仅作为可选辅色，不把日常主题定成冰蓝。深色文字用柔和但足够清楚的中性色。
- 在边缘、局部插画或背景细节表达绒感；文字、输入区表面保持平滑，避免纹理干扰阅读。
- 保留近距离目光，介绍主视觉可更偏半身与脸部，不必套用大诗音的全身站姿。猫耳应进入头像安全区，不能固定圆裁后只剩脸。
- 动作是耳朵微动、短幅轻晃、柔和呼吸。不能让整页都漂浮、缩放，也不以廉价大光晕代替柔软质感。

### 三人的共同点与差异

共同点是人物本身已有丰富的服饰、发丝、光色和材质；UI 无需再用同等密度的装饰与之竞争。三人分别可概括为“大诗音从容迎接 / 小诗音主动邀请 / 小白贴近依赖”。这些是读图后的设计解读，不替代角色设定。

它们可共享功能位置、文字尺度、图标笔画与交互状态，但需要不同的主视觉距离、线条走势、配色层级和动作节奏。只改五个强调色不够；把每人都放入相同的空白卡片模板同样不够。

### UI 参考里真正值得保留的东西

### 对现有完整项目的美化顺序建议

1. **角色介绍页**：仍以现有立绘区与资料区为基础，先改善封面焦点、背景融合、姓名层级、主要操作与档案信息的主次。资料字段、编辑、形态切换、看原图、隐私折叠和画廊入口完整保留。减少“每一个字段都同样粗边框、同样底色”的感觉，而不是删除信息。
2. **聊天页**：保留会话 / 聊天 / 状态栏及手机导航语义。角色色放在头像、选中态、头部局部装饰和立绘周围；聊天气泡与输入区域稳定可读。多角色群聊采用中性公共底，每条发言通过头像与小范围角色色区分，避免整页跟随消息跳色。
3. **小窝与画廊**：用已有内容建立封面与缩略图的视觉节奏。占位、空状态、加载态也按角色做细节统一；不把房间参考变成新功能需求。
4. **启动层**：在静态视觉方向稳定后再讨论。沿用可跳过、等待有上限、不伪造进度的原则；当前阶段不实现。

### 素材与后续 demo 的前置判断

- 四张角色参考当前均有不透明背景；不能直接假设已有透明立绘。三视图是造型核对资料，不是封面素材；含标记或水印的图不擅自擦除。
- 小诗音参考的金色轨迹、节庆文字与背景已经烘在图里；用于原型时先按完整插画构图考虑，透明立绘、独立粒子需要另备素材，不能宣称现有图能直接拆层动画。
- 大诗音当前素材偏立体渲染，小诗音与小白偏插画。第一阶段以各自现有画面成立为目标，统一 UI 的光感与比例；若未来要统一画风，列为单独的素材制作工作。
- 本目录没有紫发大诗音、偶像 / 科技版小诗音与汐子的对应参考，继续保留用户指定方向，但不从当前三张图推断未给出的造型细节。
- 之后若获准做 demo，应展示已有真实页面的美化，而非再做一个无关落地页；保留真实功能入口，用三位角色的现有素材对照。现阶段停留在方案，不改原项目和旧 demo。
