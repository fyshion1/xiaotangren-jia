建议迁移的是：单角色常驻、轻触立即反应、抚摸过程反馈、短语音和气泡、欢迎回来、休息提醒、安静模式。首页与商城里的按钮密度、多角色同时铺满屏幕不宜照搬到小窝常驻桌宠；先把单个角色的存在感和不打扰做扎实。

具体交互建议：点击到释放时若位移很小则算轻触；超过拖动阈值进入搬动，搬动期间锁定事件接收，释放时回归。抚摸用停留、路径长度和冷却判断，不能简单把连续 mousemove 都当摸头。右键显示简短菜单；聊天输入按需打开；提供托盘/快捷键恢复交互，避免穿透后再也点不回。

触摸反馈走本地动作/表情，建议目标为约 100ms 内开始；这只是验收目标，尚未测量。LLM 在后台补充台词，不能让每次摸头都等网络。语音播放需要互斥、优先级、取消和嘴部同步；提醒需要去重、冷却、勿扰和睡眠恢复处理。这些规则才是兽耳感受的主要来源。

**接入小窝应怎样修正**

features/desktop-pet 独立项目 + Python 入口仍合理，命令应遵循真实 runner 的 python -m module <command> 结构。启动/停止、日志、配置进入现有面板。Python 包装器不自动解决进程树：现有 _stop_one 的强杀主要针对父进程；Electron 是多进程，需确保父退出时宿主结束、渲染进程回收，并处理异常与单实例。Windows 可考虑 Job Object，不能只在 finally terminate 一下就宣称可靠。

gateway 虽然底层是 [node,script]，但现代码还夹有 SnowLuma 环境变量、QQ 账号认领、端口等待等特定语义。“填 electron.exe 就能干净接入”因此不成立，推荐不用它承载桌宠。

第一版可让桌面窗口使用现有服务的 /api/nest/chat 和 /api/voice/tts，增加薄的身体事件层：pet/head、drag/start/end、speak/start/end/cancel、reminder、idle/quiet 等。动作应限定白名单，有优先级与截止时间；聊天回复与动作播放分开调度。聊天 API 已要求角色与会话信息，模型绑定还存在本地前端配置，不能假定桌面窗口会自动继承浏览器 localStorage。

前端静态资源目前通过 Vite 的 apply:'serve' 插件提供 /assets；生产构建不会自动复制这些模型。正式宿主应使用受限的本地资源服务/协议或明确的外部资源目录。优先复用已有后端，确有资源服务需要时才另开一个；避免为了包装 Electron 再复制一套业务服务。

模型触摸区和操作系统穿透是两个判定：Head/Body 用于角色语义，alpha/mask 用于判断是否挡住下层应用。VRM 的 raycast 同样不等于纹理 alpha 精确命中。应先用低分辨率 mask 或受限采样避免每次 mousemove 都同步读整幅 GPU 缓冲，边缘做适度容差；拖动、菜单和输入期间保持事件接收。

不应只按“光标远离”降帧；还需依据说话、动作、拖动、静止、最小化、锁屏和电源状态。完全遮挡的可靠检测依赖平台，不能把它当作已有能力。每帧扫描所有 Live2D drawable 来重新居中也容易导致脚底漂移，宠物宜保持稳定脚底锚点和相对固定尺度。

**建议的第一版范围和验收**

先用 Electron 稳定 Live2D 单角色：修复闪烁和 DPR、稳定脚底，接轻触/抚摸、拖动、眼神、语音气泡、回家欢迎/休息提醒、勿扰和托盘恢复。VRM 保留加载能力，完整动画身体另成一个明确阶段。自定义角色所需的表情、动作、触摸区和语音素材映射必须单独定义；Haru 的 F01/Head 名称不是所有模型的通用规范。Unity 房间沿既有 MVP 独立推进，接入大脑不以桌宠完成为前提。

进入实现后应验收：连续运行与多次换模型、DPR 1/1.25/1.5/2 和真实混合 DPI 多屏、透明空白点击到下层、头发/半透明边缘、快速划过后马上点击、拖动不穿透、菜单/气泡交互、断网与后端重启、语音打断、休眠恢复、强制结束后无残留进程。测量 GPU/CPU/内存、输入响应和包体时须固定模型、窗口面积、帧率与硬件。

原先“两三天到一周”只能算特定经验估计，不能作为承诺。当前首先要消掉已复现的渲染问题，再用一个真正的 Windows 透明窗口原型测输入；通过后才适合估稳定版本工期。

素材许可按每个模型、动作和 SDK 实际条款核对。当前继续使用本机素材纪律；不能泛化为“所有 Cubism 官方样例都禁止再分发”，也不能从代码开源推导素材可用。

**Claude Code 参考意见的采纳与修正**

用户随后提供的 Claude Code 报告作为参考意见，不视为新增实测证据：

- 采纳 Electron、角色主导、触点语义分层、持续状态和表现层拆分。表现层应区分角色身份/语义与模型执行器；但既有 React 组件有渲染缺陷，不能按“已经跑通”直接搬运。
- “常驻唤醒、不点按钮就能打断”“跨天好感度/情绪记忆”是待选择的产品能力，本次没有验证它们是兽耳现有功能。语音打断可通过点击或按键实现，不等于必须监听麦克风；常驻唤醒不纳入已确认第一版范围。
- 官网无法由文本抓取读到正文不等于没有可用产品资料。本次系统 Chrome 截图读到介绍内容，并直接读取了电脑版官方宣传图；仍不推断其客户端内部技术栈。
- 不采用 Mate-Engine 源码作为底座，但它的混合许可不因“同用 Unity”或“放入 features”自动约束独立开发的 DashiyinRoom。需要审查的是具体复制、链接或分发的代码和素材。
- 不采纳“只有点击穿透最难”与“两三天到一周”作为工期结论：本次渲染回归、DPI、进程树、语音调度和资源部署均有具体待办。
- Haru/Hiyori/Alicia 等样例继续遵守本地素材纪律，不进入桌宠仓库或构建产物；不因技术可加载就变更素材分发边界。
- 暂不扩搜 Open-LLM-VTuber、Amica、VPet。当前选型已明确，新增候选只有在出现具体未解决能力时再补查。
