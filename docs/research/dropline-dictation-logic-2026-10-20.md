# Dropline 口述整理逻辑调研

日期：2026-10-20。依据：[中文官网](https://dropline.fish.audio/zh-CN/)、[公开 API 文档](https://dropline.fish.audio/docs/)（标注更新于 2026-10-08）、[隐私政策](https://dropline.fish.audio/privacy/)。未安装、未调用接口、未实测识别效果。在本次 GitHub 仓库检索中未找到可核验的 Dropline 实现源码，以下区分文档事实与建议。

## 有证据的处理逻辑

- 口述模式做最小整理：去填充词、口吃重复、合并明确改口、修正听错的词、数字与标点规范化、按目标应用排版。官网宣称拿不准保留原话；这属于产品承诺，未验证执行准确率。
- 编辑模式独立：语音作为编辑指令，选中文字作为被操作对象；可以改写、翻译、删除。避免把正常口述误当成命令。
- `POST /v1/dictate` 输入录音及可选上下文。返回 `final_text`、`transcript`、`rewrite.status`、耗时；文档明确也有一步生成整理文本的路径，此时 `transcript.text` 就是整理结果，语言为空。不能一概声称内部固定使用两个模型串行处理。
- 上下文包括应用名、窗口标题、网址、光标前后文本、选中文本、屏幕或文档文字。配合个人词典和记忆辅助识别与整理。未公开具体模型、提示词、检索算法及保真校验规则。
- 字典包含标准词及可能听错的别名。`/v1/context` 异步从工作文本学习词语及近期主题；文档称主题记忆约两周，不作为用户亲口说过的话。不是把所有罕见词都收进词典，而是筛选容易识别错的词；用户删除过的词不自动加回。同一文本一小时内重复提交会跳过。
- 场景影响格式：聊天简洁、邮件标点完整、文档可排列表，终端单行。接口提供中英文间距、全半角标点、单行等选项。
- 桌面应用通过粘贴输入并恢复剪贴板。官网称只交付整理完成的文字；API 文档却明确 `rewrite.status` 为 skipped/rejected/failed 时 `final_text` 是转写，调用方需自己判断是否接受。两种交付行为不能混为一谈。

## “去口水话”为什么不是查表删除

官网演示“嗯那个那就明天下午三点，不对，四点半吧”得到“那就明天下午 4:30 吧”：它不仅删除填充词，还识别了改口所替换的时间范围。

以下为本项目设计建议，不是已核验的 Dropline 算法：

- “嗯，那个，我想问……”可能清理；“那个文件不要删”的“那个”应保留。
- “不，不要删”应保留否定；“真的真的很开心”可能是强调，不能一律去重。
- “三点，不对，四点半”是替换；“周四不行，周五也不行”不能仅保留最后日期。
- 保留原转写与整理结果；保护否定、金额、日期、人名、语气强弱。没有明确修正依据时，不能让近期记忆覆盖当前发言。

## 与本项目的关系

它解决的是用户口述到书面输入的整理，不是自动减少 AI 回复里的空话。后者仍需控制回答策略和提示词。

建议将强整理用于语音输入文字框或明确的口述模式。桌宠实时陪聊宜轻整理，保留“嗯”“唉”、犹豫和强调等情绪信号；这些内容对陪伴对话有价值。原转写、整理文本、用于后续记忆提取的事实应能区分来源，不让整理结果冒充逐字原话。

可以借鉴最小改动、明确改口、词典别名、上下文临时使用与长期学习分开、删除偏好与去重等逻辑。无需为此先迁移语音链路，也不应在未测延迟前为每轮通话增加串行整理请求。

若直接使用其服务，官网说明录音、词典及相关应用上下文会发送云端；模型训练选项通常默认开启（欧洲默认关闭），可在设置关闭。这是服务选择相关的实际数据流，不是本地清洗工具。
