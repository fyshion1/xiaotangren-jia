# 通用本体、插件与个人数据边界

2026-10-24。依据用户本轮方向与现有文档、代码做集中梳理。本轮不迁移数据、不修改运行路径，不表示下述目标已实现。

## 已明确的产品方向

本体作为通用框架提供通用 API，公开源码并持续更新；主题、桌宠等能力独立插件化、分别更新。个人角色图片、设定和其他私人数据需要统一管理，不能因为更新本体或关闭主题而丢失。

框架名称后续确定为 Shionarium；最终目录名和第三方插件 API 的稳定版本仍待落实。许可证沿既有记录另行落实，本轮不重新授权任何文件。公共市场及「个人自用优先、保留云部署空间」约定见[后续方向](public-market-and-self-hosting-2026-10-24.md)。

## 现状与依据

| 内容 | 当前存放或实现 | 边界问题 |
| --- | --- | --- |
| 已保存的角色和用户身份 | `backend/data/xiaotangren.db` 的 `characters`、`profiles`，JSON 档案 | 有持久化和编辑 API，但尚无独立、完整的角色资产管理层 |
| 默认人设、身份、回复风格 | `features/xiaotangren-theme/xiaotangren_theme/` | 目前与主题捆绑；不是纯视觉主题 |
| 默认头像、立绘 | `features/xiaotangren-theme/public/characters/` | 已有档案仍可能引用主题路径，停用后图片不再提供 |
| 上传附件 | `backend/data/attachments/`；`/api/attachments`、`/api/files` | 已集中一部分媒体，但未覆盖默认角色素材 |
| 聊天、设置等 | 主 SQLite 及 `backend/data/` 下其他运行文件 | 数据路径仍有多处硬编码，尚无覆盖所有服务的统一根目录配置 |
| 个人事实和知识文档 | 默认根目录 `个人数据库/` | 支持 `PERSONAL_DATABASE_ROOT`，可继续作为跨项目资料库 |
| 正式记忆文档及审批流程 | 默认根目录 `个人记忆库/` | 支持 `PERSONAL_MEMORY_ROOT`，不能与事实、知识资料混为同一种数据 |
| 部分界面偏好 | 当前浏览器 localStorage | 不随 Git 或仅服务端备份自动保存 |

实际发给模型的提示词由档案、当前身份、记忆、历史和规则等组装，并非所有内容都来自一份角色设定文件。源码中的设定原稿不等于用户编辑后的数据库，也不等于最终模型请求。

已有基础：存储管理页可管理聊天和附件；`tools/create_personal_snapshot.py` 可生成含源码与私人数据的本地快照。它们分别解决清理与备份，不代表角色素材和个人数据已经完全统一。

## 推荐的职责边界

1. **本体**：角色与身份存储、资源登记、会话、模型连接、记忆服务、配置、授权和插件生命周期；提供带版本的通用契约。

2026-10-24 后续确认：记忆的存储、检索、审批、聊天注入及管理界面均保留本体；只将额外个人档案和个人数据库管理设为可选插件，避免基础聊天依赖一组必装扩展。落地边界见[个人资料插件说明](../guides/personal-data-plugins.md)。
2. **主题**：颜色、字体、图标、装饰与布局。停用仅改变展示，不改变角色、人设或记忆。
3. **角色包**：可导入的角色模板、头像、立绘和来源信息。导入后创建用户持有的档案及资源副本；后续包更新不覆盖个人编辑。
4. **功能插件**：桌宠、QQ 桥、联网工具等，通过本体 API 使用被允许的能力。功能私有数据按插件 ID 隔离，共享角色和媒体使用资源 ID/API，避免直接依赖本体 SQLite 表或仓库相对路径。
5. **个人数据**：逻辑统一登记、备份和管理，生命周期独立于本体源码及插件安装文件。资料可在外部目录，不强制把已有跨项目知识库搬进仓库。

小糖人私人体验可由主题、角色包和插件配置组合。角色仅出现在用户已导入的数据和相应可选包中，不作为通用本体的固定品牌。

## 存储目标草案

建议用统一的工作区数据根目录配置承接持久数据，并保留外部资料库路径配置。以下仅作职责示意，尚未定名或创建：

```text
workspace-data/
  databases/         # 档案、会话、设置、资源索引等
  assets/            # 用户持有的头像、立绘及其他持久媒体
  plugins/<id>/      # 插件私有持久状态
  backups/           # 用户数据备份
```

插件安装文件、可重新下载的模型、缓存和用户持久数据应分别管理；统一入口不意味着所有格式必须变成 JSON 或所有文件必须物理搬到同一目录。角色档案继续使用 SQLite 也可行，不维护一份会与数据库互相覆盖的人设副本。

资源 API 需要稳定 ID、归属、用途、来源、引用关系及删除检查。删除或卸载前应区分“安装包附带素材”和“用户已导入素材”，避免把仍被角色引用的头像当缓存清理。

## 渐进顺序与验收

1. 盘点数据路径与引用关系，建立统一路径解析和备份清单，兼容现有位置。先验证备份及恢复，再执行迁移。
2. 将角色模板与主题解耦，导入素材进入用户资源层。验证关闭、卸载主题后，已有头像、立绘和角色设定继续可用。
3. 收敛通用档案、资源、模型和活动/记忆 API，记录接口版本、身份范围和错误返回；再逐个适配桌宠、QQ 等。
4. 明确各插件安装、升级、停用、卸载与数据保留规则；升级包不得静默覆盖私人档案。主仓库与各插件分别发布版本和兼容范围。

现有固定路径加载器和宿主 SDK 仍是过渡实现，不宣称已经有稳定第三方插件市场。优先做真实使用链路的边界整理，避免先建设一个脱离当前功能的大型 SDK。
