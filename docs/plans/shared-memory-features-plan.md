# 多端并发与 features 共享记忆方案

记录日期：2026-10-19。状态：已完成第一版施工，当前可用行为及边界见文末「施工结果」；前文保留总体设计，不能把所有设计目标都视为已经实现。

## 目标与现状

网页、QQ 桥、桌宠及未来 features 使用同一身份、人设和记忆体系。功能来源用于追溯与检索，不应天然成为记忆隔离边界。用户身份与已有角色可见范围仍须遵守；真实经历、游戏剧情、假设练习必须保留各自的语境。

2026-10-19 检查结果：

- `/api/chat/session/turn` 和 `/stream` 有进程内全局轮次锁、请求编号去重及消息事务；QQ 群聊路由与桌宠使用它。QQ 具体角色的旧路由仍需迁移核对，不能视为所有 QQ 路径均已统一。
- 网页仍分别调用 `/api/messages` 与 `/api/chat`，生成上下文来自浏览器；三秒轮询同步在生成期间暂停，无法保证发出时已经包含其他端的新消息。
- SQLite 单次事务加锁不等于完整轮次一致。现有全局轮次锁会让不同会话互相等待，且不跨进程。
- 每日整理已按身份、会话、日期、功能合并进行中的任务，支持增量进度；文件写入采用原子替换，审核检查 revision，后台避让人工编辑。待办仍在内存，重启后需人工重试。
- 旧规范把 `feature_id` 用作记忆隔离键，日语插件默认关闭记忆，现有提炼调用也带功能命名空间；不具备跨功能统一每日回顾。
- 日语插件本地 `threads.turns` 保存问答，`summary` 保存总结；它们目前不等于本体当天聊天归档。插件 `extract_memories` 仍发送 `text/preview` 等旧字段，落地时必须与当前本体 `ExtractRequest` 校对，不能只打开开关便认为接通。

验证基线：会话测试 12 项、记忆工作流测试 28 项通过；未做多端联合并发压力测试。

## 一、统一聊天轮次

所有呈现端最终进入服务端统一的“接收 → 持久化用户消息 → 读取权威上下文 → 生成 → 持久化回复 → 通知各端”流程。网页的图片、视频、重新生成、编辑重发也纳入迁移。保留模型选择等现有能力。

每个请求持有稳定的 request_id，失败重试复用编号；消息与轮次状态一起提交，回复记录关联触发消息。各端依赖服务端顺序号与状态同步，展示排队、生成、完成和失败。

同会话严格串行。跨会话若涉及同一用户与同一角色的即时认知，则协调该角色的上下文读取和状态提交；多个角色共同参与时按固定顺序获取协调权限，避免死锁。耗时无关工具任务可并行，回执作为新事件提交。锁定范围需通过实际延迟验证，避免长期使用全局大锁。

单纯加锁不会让私聊知道群聊刚发生的事：还需在角色可见范围内读取共享近期事件。每轮记录历史截止位置及记忆版本，发生纠正时保留新旧证据关系。多 worker 前将任务领取、去重和提交协调移到持久化存储；Python 内存锁不足以承担该职责。

## 二、features 的统一接入契约

插件仍是独立项目，通过 HTTP 使用大脑。新功能无需复制记忆库或实现另一套人格。

接入分两条通路，单个功能可以同时使用：

| 通路 | 用途 | 本体处理 |
|---|---|---|
| 对话轮次 | QQ、桌宠、学习答疑等用户与角色的实际交流 | 统一生成和落库，保留用户与助手角色、原文及关联关系 |
| 活动事件 | 学习完成、练习成绩、看过视频、游戏事件、工具执行结果 | 幂等接收、存证、归入当天时间线，必要时生成摘要 |

来源字段 `source_feature_id` 与记忆可见范围分离。现有 `feature_id` 历史上参与隔离，必须新增显式映射与兼容层，不能直接改名或全部置空。模型配置归属也与记忆归属分离。

拟议活动契约（尚未实现）：`POST /api/memory/events`。

必需信息：`event_id`、`source_feature_id`、显式 `persona_id`、带时区的 `occurred_at`、`kind`、实际原文或结构化事实。按身份、功能、事件编号建立唯一约束。会话/线程编号、相关角色、原始记录编号、附件引用、练习主题、完成状态及事件修订号按需提供。

服务端校验身份、功能、字段、可见范围和附件引用；不信任插件自行宣称“已批准长期记忆”。同一来源事件修订时递增版本，保留证据链；不同事件即使文本相同也不盲目去重。历史导入保留发生时间，接收时间另记。日期统一按北京时间分组。

交付语义：收到本体持久化确认后才标记已同步；插件保留待同步队列并用同一事件编号重试，本体用持久化待办处理摘要。重复发送不重复计入当天经历，重启能恢复。实际聊天轮次只归档一次，活动摘要引用它，避免再伪装成一条用户发言重复导入。

新功能声明需要的能力（对话、活动上报、附件等），提供明确身份与来源、稳定编号、原始证据、重试和修订行为，即可复用同一流程。功能专用数据库可继续负责练习状态、词卡和成绩；统一记忆入口保存足以独立追溯的原文/事实快照，不能只存可能失效的插件本地链接。

## 三、功能内容如何归入当天记忆

沿用现有 01/02/03 工作流，不另建按功能隔离的人格记忆。

1. **01 原文与活动证据**：保存实际问题、回答、追问、练习作答和已确认结果。保留功能来源、时间与原编号，支持从当天时间线展开查看。按来源组织文件只是归档方式，检索可跨来源聚合。
2. **02 当天经历摘要**：跨 QQ、网页、桌宠及学习功能，以身份、北京时间日期和可见范围聚合；主题/学习活动下保留事件与证据引用。增量更新当日摘要，按修订号避免旧结果覆盖新事实，人工修订优先。
3. **03 长期记忆候选**：从当天经历中挑出长期目标、明确约定、持续偏好、重要共同经历，继续人工审核后启用。不把每个题目答案都塞入长期人格记忆。

近期回忆可以读取有证据的 01/02，必须作为“来源资料/当日活动摘要”明确传入模型，不能冒充已审核的长期事实。该能力需要新增受控检索入口，现有“未审核不注入长期记忆”的规则不变。查询“今天学了什么”按时间与活动检索；查询“具体问过什么”进一步取问题清单和原文。上下文预算内返回命中片段，细节分页，不把全天所有教学内容常驻提示词。

教学提示词、自动出题模板、工具参数不是用户真实发言。角色讲解的知识不自动变成用户的信念；问过某题不代表掌握，批改正确一次不代表长期熟练。虚构例句、角色扮演剧情与现实生活事实分别标注，避免混淆。

## 四、日语学习例子

以下是假设数据，不能导入为真实经历：当天用户问“は和が怎么区分”，追问“这里为什么不能用は”，又问“ている是否总表示正在进行”，完成三道练习，答对两道。

01 保存三次具体提问、各次回答、题目与作答、实际批改结果、参与角色与时间。02 可归纳为：

> 今天在日语学习功能中与大诗音复习了「は／が」和「ている」。具体问了助词区别、某句为何不能用「は」、以及「ている」的状态含义；三题答对两题，其中一题仍需复习。附对应问答和练习编号。

缺少答题记录时不能生成“三题答对两题”；只有问题没有追问或批改时只能记“询问/讨论了”。短期在 QQ 问“今天日语问了什么”，通过共享近期事件即可准确回顾，不必等长期审核。

若用户另有明确表述“准备十二月考 N2，之后每天一起复习”，再形成长期目标/约定候选。当天题目与知识讲解仍留在可检索原文与学习资料中。

日语插件适配顺序：核对提炼旧协议 → 本体接收活动与原文 → 以线程/问答/练习稳定编号增量同步 → 当天摘要与跨端近期检索 → 长期候选审核。历史导入单独回填原发生日期；默认开启策略在实施配置时明确，不因本方案立即改变现有开关。

## 五、实施顺序与验收

优先统一网页/QQ/桌宠轮次与去重，再建立活动接收和持久化任务；以日语功能验证，之后形成所有 features 共用的适配器说明与示例。旧的游戏/外设隔离资料保留语境和原归属，经兼容映射决定共享可见性，不批量自动批准历史候选。

验收至少覆盖：三端同时发送不丢失且上下文顺序可解释；同请求重试只写一次；不同活动并行不覆盖；同事件修订不倒退；跨功能同主题合并但不同事件不误合并；学习细节可追溯；成绩只来自记录；跨日/延迟上报日期正确；身份与角色可见范围正确；剧情不混入现实事实；未审核长期候选不被当成正式事实；离线重试/重启恢复；删除源记录后同步清理派生摘要与索引，正式记忆沿用现有独立管理规则。

## 六、施工结果（2026-10-19）

已实现：

- 本体 `activity_events` 持久化事件与修订、来源策略；事件按发生时间（北京时间到秒）及本体全局序号排序。重试去重、同版本异内容冲突拒绝、修订不倒退、延迟上报与跨日修正均有测试。
- `个人记忆库 → 当天经历与来源` 提供来源总控、原始活动/待审核/正式记忆计数、当日跨来源时间线、搜索与分页、查看依据、提交长期审核、单条删除预览。停用/卸载不会清空历史；来源接收、整理、召回和归档独立控制。来源计数允许一条多源记忆同时计入多个来源，不应求和当总数。
- 来源召回开关作用于近期事件和有来源依据的已审核记忆。多源正式记忆采用保守规则：任一来源关闭/归档时暂不注入整条，避免剩余摘要泄露被关闭来源的事实。以后可重新核对剩余证据后拆分，不自动猜测。
- 新普通网页发送（包括已落库图片和视频）走 `/api/chat/session/web-stream`；服务端读取权威历史、保存回复并返回消息编号，前端不再重复保存助手消息。失败在当前页面复用请求编号；刷新后的跨页面重试编号尚不持久化。重新生成支持历史截止消息；编辑/删除步骤仍沿用既有消息接口，并非完整跨端编辑事务。
- 网页、桌宠、QQ 回复及 `/api/nest/chat` 使用 SQLite 租约协调同身份、重叠角色，群聊一起获取角色集合；不相干角色可并行，租约定期续期并在异常/取消时释放。QQ 新桥接代码将租约延续到发送完成，发送前校验/续期，finish 回执释放；失联 120 秒过期，旧客户端保留兼容路径（仅生成阶段协调）。不声称 QQ 网络发送实现了严格 exactly-once。
- QQ 当前轮次的共享近期资料按已选消息的全局事件序号截取，避免之后到达的补充提前混入旧轮。
- 日语学习开关仍保留原有默认关闭及用户设置。启用后同步实际答疑问答、词汇/语法讲解请求、例句/练习生成请求、造句批改、词卡/语法复习自评和登记成绩。提问保留当时所看的背景，练习例句标记 exercise；原文先进入插件 SQLite outbox，后台十秒重试，身份在动作开始前确定，不在重试时切换身份。复习自评不会解释为客观掌握。不能确定身份时不向任意身份补记。
- 当前后台同步针对上述新活动。已保存的旧线程/卡片/成绩不自动回填；其他插件可使用通用事件接口逐步适配。旧聊天可用「01 源记忆 → 补齐旧聊天归档」回填本体时间线，未知来源保守记为本体，不凭内容猜插件。

当天归纳采用按来源/主题归组、附时间与证据的确定性投影，不额外调用模型写一篇全天散文；每次由有效事件重建，因此不存在后台旧摘要覆盖新摘要的问题，也没有待恢复的投影任务。聊天按角色可见范围读取当天/昨天/显式日期的原始活动依据，预算不足时注明仅展示部分，完整内容在时间线分页查询。当前没有跨插件语义事件自动合并与事实纠正推断；这类关系由证据修订和人工核对保证。

原有 `memory_daily` 的 LLM 长期候选提炼仍沿用现有队列和人工重试机制；本次没有把它改成自动重启恢复的持久化调度器。未来的后台语义合并/自动长期提炼必须另接可恢复任务，不能依赖内存队列作完成承诺。

删除活动会清除该事件各版本的正文，并保留无内容的删除标记阻止旧上报复活。关联本体聊天时调用原有消息/附件级联清理；当天投影立即反映删除。长期候选、已审核记忆以及插件自己的本地学习账本继续独立管理，删除确认框明确提示，不默默连带删除。

接口与新插件适配示例见 [features 共享活动契约](../integrations/feature-memory-api.md)。更新后需要重启后端、QQ 桥及日语插件并刷新网页；未执行真实 QQ 发信或调用收费模型作为验收。

验证记录：后端全量 246 项、日语插件 70 项、QQ 桥 84 项、流式传输 5 项通过；前端生产构建通过。Chrome 离线浏览器验证涵盖统一网页发送后不重复保存回复、来源开关、当天活动、桌面/390/320 像素布局；所有 API 被模拟，不写真实资料。Windows 测试使用 Python UTF-8 模式以支持日志中的中文与表情符号。
