# 发布与知识产权跟进

记录日期：2026-10-18。适用背景：中国大陆个人开发者；未来发布地、经营主体或商业模式变化时重新检查。

本文记录用户已表达的目标、当前建议和待办，不代表已选定许可证、已获得第三方授权或已完成法律审查。尚未发布或改变任何代码、素材的许可。

## 1. 已确认的长期目标

- 项目首先是自己喜欢、每天使用、长期维护的个人作品，也是求职作品。
- 希望逐步增加个人影响力，保留未来变现的可能。
- 尚未决定立即公开完整源码、立即收费或采用某个开源许可证。
- 美术资源的理想优先级：**自己画 ＞＞＞ AI 辅助生成 ＞＞ 购买明确著作权或商业授权**。
- 极少或不使用网图，重视完整、可核实的版权来源。
- 当前不急于公开或变现，优先继续打磨产品；对法律、侵权和许可证存在疑点的部分，倾向逐步替换为自主内容或来源与许可明确的方案。
- “自主化”的目标是核心内容可控、权属清楚、使用有据，而不是重写操作系统、语言、框架和全部依赖。不能保证绝无争议，但可以减少未处理的授权疑点，并保留解释和举证依据。
- 最新决定：项目目前尚未完善，先进行约半年至一年的内部深度使用，以自己的真实使用体验推动改进；这是大致观察周期，不是发布承诺或截止日期。
- 当前不安排宣传、公开测试或正式发布任务，先深入使用后再判断。音色方案暂待后续研究。
- Live2D 定位为 `features` 中可选导入、可用可不用的功能项目，不作为主体产品的必需能力；这是用户确认的产品定位，不代表本轮已核验全部代码和打包边界。

注意：“购买著作权”和“获得可商用许可”是不同交易。非独占商用许可可能允许原作者把相同素材卖给他人，并不自动满足独占角色品牌的需要。

## 2. 当前推荐路线

**先把它做好为可展示的个人产品；按模块决定公开范围；原创角色资产单独管理；为以后收费保留选择。**

这是一项建议，不是要求永久闭源。求职展示与传播影响力，不以公开全部源码为前提。

**当前实际阶段是内部打磨，以下 A/B/C 是未来候选路径，不是立即执行的发布计划。**

### 当前：先深入使用，再决定展示与发布

- 先用约半年至一年观察真实需求、长期稳定性、记忆质量、语音体验和维护成本；不要求凑满期限，也不要求到期立即发布。
- 开发记录以服务自己的改进为主：记下常用功能、长期不用的功能、具体故障及修复结果，保留创作和权属证据即可，不额外增加固定宣传负担。
- 阶段回顾可围绕三个问题：自己是否持续使用？核心流程是否可靠？哪些功能值得继续投入？回顾频率自行决定。
- 将来有意展示时，可以先发布已经稳定的小成果或创作过程，并如实说明开发状态；不必公开全部源码或交付完整产品。
- 正式发布应以核心价值清楚、基本体验稳定、许可与资源问题处理完、能够接收反馈为依据，不以热度或功能数量为依据。
- 用户现阶段选择先用再说，暂不推进此前提到的少量外部体验邀请。将来给朋友安装、分享代码或文件时，另行检查交付和分发条件；“内部测试”称呼本身不自动免除这些义务。
- Live2D 即使是可选 feature，其 Core、模型和相关素材仍按实际取得、集成及分发方式检查许可。可选架构便于独立替换和控制交付范围，但不是当然的许可豁免。

关于“早宣传还是打磨后出山”的讨论结论：可以耐心打磨产品，将来酌情公开可靠成果，不必把宣传、源码公开和正式发布绑成同一次行动。当前没有开始宣传的要求。

### 阶段 A：求职展示与整理

- 保留完整开发仓库；另做经过清理的展示页、演示视频和必要的演示版本。
- 展示真实功能、架构、自己解决的问题与实际验证结果；如实说明 AI 辅助开发及自己承担的工作。
- 确保截图、视频、演示包中的模型、图片、字体、音乐、配音也有相应展示或分发权限。
- 需要展示代码时，可选择权属明确的模块或准备独立技术样例。不要为展示少量代码而公开整个开发目录。
- 不公开个人数据库、聊天记录、API Key、私人角色资料及本机配置；当前文件不含敏感内容也不代表 Git 历史安全。

### 阶段 B：建立影响力

- 根据维护能力发布开发日志、功能演示、架构文章和明确边界的开源模块。
- 若希望某个通用模块被广泛使用，可考虑 MIT / Apache-2.0；接受别人依许可商用、修改和分发的结果。
- 产品主体与核心角色素材可以继续单独授权。
- 如果接受整个产品被合法 fork、修改和再发布，再考虑产品级开源，而非只为了 star 仓促决定。

### 阶段 C：免费测试或商业发布

- 免费测试版也需要先完成第三方授权和分发检查；免费不是免责条件。
- 可能的收入方向：产品高级功能、维护与支持、授权明确的角色内容、定制服务。具体模式以后再定。
- 商业发布前复核依赖、Live2D、模型及语音服务条款，并准备适合实际交易方式的产品许可、隐私说明和售后规则。

## 3. 许可证怎么选

| 期待的行为 | 可考虑的许可 | 必须接受的边界 |
| --- | --- | --- |
| 允许他人自由使用、商用、闭源集成 | MIT / Apache-2.0 | 合规商业复用不是侵权；Apache-2.0 有明确专利条款 |
| 分发相关修改或组合作品时承担源码义务 | GPL-3.0 | 允许收费；具体范围取决于组合关系，不是整个仓库一概适用 |
| 修改版本通过网络交互也承担对应源码义务 | AGPL-3.0 | 允许商用；不是所有周边系统都会自动适用 |
| 公开源码，但限制未经许可的商业转售 | 明确的源码可见许可 / 商业许可 | 通常不能称为标准开源；需要清楚定义允许与禁止事项 |
| 控制主体产品的商业发行 | 私有源码＋产品使用许可 | 仍须满足第三方组件条件，不能凭自己的协议覆盖 GPL 等义务 |

当前不直接选定产品级许可证。关键问题是：**是否接受别人遵守许可证后，用公开代码制作竞争产品并收费？**

不要把 GPL/AGPL 当作“禁止盗卖”的非商用协议；也不要认为后来删仓库或换许可证就能追溯收回旧版本已授予的合规授权。

无许可证通常适用默认版权保护，但 GitHub 公开仓库仍受平台查看、fork 等条款约束。依赖 `package.json` 中的 `private: true` 也不能代替许可证。

未来可将许可文件拆成：

```text
LICENSE                 自有代码的许可及适用范围
ASSETS-LICENSE.md       原创美术、模型、配音的授权规则
THIRD_PARTY_NOTICES.md  第三方组件与素材清单
licenses/              第三方许可证原文
```

这只是建议结构，尚未创建或授予任何许可。根目录文件应明确排除第三方与另行授权内容，不写“全部内容均归本人所有”。

若未来接受外部贡献，先明确贡献许可；希望对外部贡献也能另售商业授权时，需要适当的贡献者协议或其他授权安排，不能事后默认自己拥有重授权权利。

CLA 可以是授权协议，不一定转让著作权；DCO 主要证明贡献者有权按项目许可提交贡献，不自动赋予项目方另售商业许可的权利，两者不能互相替代。

## 5. 美术权利管理：按你的偏好制定

### 自己画：作为长期核心角色的首选

- 保存角色设定、草图、分层文件、过程稿和导出版本，记录作者与完成时间。
- 自己的角色设计与 Live2D 拆件、建模、动作可能由不同人完成，逐项确认权利。
- 使用外部字体、贴图、素材笔刷、模型配件时仍检查许可；“自己制作”不等于其中所有组件均为原创。
- 对核心原创角色考虑单独办理美术作品登记；软件软著不自动覆盖所有角色美术。

### AI 辅助：保存人的创作过程和工具条款

- 保存使用的服务或模型、版本、生成日期、当时适用条款、提示词、迭代和人工修改记录。
- 使用自己绘制或有授权的参考图，避免把他人的特定角色或插画直接作为可自由使用的素材。
- 区分“服务允许商用”“输出不侵权”“输出具有著作权”“自己拥有独占权”四个问题，不能互相替代。
- 中国已有依据具体人的创作投入认定 AI 图片受保护的个案，但不能据此断言每张 AI 图片都受保护；登记也不自动消除争议。
- 高价值角色优先增加自己的设计、重绘和持续创作，诚实记录 AI 参与程度。

### 约稿：只接受满足用途的书面安排

现行《著作权法》第十九条规定，委托作品归属由合同约定；没有明确约定，著作权属于受托人。付款、交付 PSD 或口头说“买断”均不足以取代清晰合同。

合同至少明确：

- 具体作品与源文件交付范围，作者和签约主体。
- 哪些著作财产权转让，或授予何种独占 / 非独占许可；作者人身权依法处理。
- 修改权属于著作人身权，不与改编权等财产权一起笼统写成“全部转让”；应具体约定作者同意的修改、拆件、重绘、建模范围与署名方式。
- 商用、软件内嵌、宣传、收费发行、周边及续作权限。
- 改服装、拆件、Live2D / 3D 建模、动作等修改与衍生制作权限。
- 是否允许交给其他承包商制作、是否允许再许可及最终用户使用；公开源文件须单列。
- 地域、期限、平台、署名方式及展示作品集规则。
- 第三方素材与 AI 使用披露、权利保证、侵权处理和违约责任。

若目的是建立独占角色品牌，应优先争取明确的财产权转让，或覆盖业务需要的独占许可，不能只买普通商用使用权。

范围足够的使用许可也可以支持商业产品，并非所有约稿都必须买断。是否独占、是否允许修改和分发，才是需要逐项判断的内容。

## 6. 软著、品牌与证据怎么搭

### 软件著作权登记

- 著作权原则上自开发完成产生，不必先登记才有权利。
- 对稳定版本办理登记，保留与登记一致的代码快照、版本号、说明文档和权属材料。
- 一般提交申请材料、身份及权属证明、源程序与文档鉴别材料。登记办法规定通常为源程序和一种文档前后各连续 30 页，不足 60 页则全部提交；具体格式、流程以办理时官方要求为准。
- 登记是权利证明材料，不是功能创意的垄断凭证，也不把第三方内容变成自己的原创。
- 有职务开发、共同开发、外包或 AI 辅助情况时，如实整理归属和实际创作证据。
- 普通软件著作权登记费自 2017 年起停征；代理等服务费另计，实际办理要求以当时官方平台为准。
- 新版本符合条件的原创内容不因未登记就失去著作权。实质升级时可考虑另行申请版本登记，不能把信息变更登记当作所有升级的通用办法。
- 证书是初步证明，不保证胜诉或固定比例的举证成本减免；Git 时间也可修改，需与其他证据共同使用。

### 产品名称、Logo 与角色品牌

- 品牌稳定后先检索近似商标，再考虑按实际业务选择类别申请。
- 软著不等于名称、Logo 已获商标保护；域名、GitHub 用户名也不等于商标权。
- 可下载软件通常关注第 9 类，软件开发、软件即服务等通常关注第 42 类；第 41 类主要涉及教育、娱乐等，并不泛指所有在线服务。最终按具体业务和申报项目选择。

### 日常证据

- 保留 Git 历史、设计记录、源文件、合同、付款与交付记录。
- 保存第三方素材取得时的页面、许可原文、版本和来源 URL。
- 对主要发布版本保存文件清单和哈希；必要时结合可信时间戳或公证。
- Git 时间和哈希都不是单独充分的权属证明，需要和其他证据互相印证。

### 遇到搬运或盗卖

先保存侵权页面、账号、下载文件、售价、传播和交易证据，再区分合法开源复用、许可证违约、盗用美术和品牌冒用。依据对应权利向平台投诉，重大争议再考虑律师函或诉讼。GitHub 版权投诉遵循其 DMCA 流程，不能只因对方做同类功能就投诉。

## 7. 合规复用：不用重写所有轮子

**合规复用本来就是软件工程的一部分。许可证是权利人授予的使用依据；满足条件的复用，不因代码来自别人就成为侵权。** 自有产品不要求每一行代码都由自己独立完成，也不要求拥有依赖的著作权。

### 区分自己拥有和有权使用

- 对自己原创的代码、美术和文档，主张有证据支持的相应权利。
- 对第三方库和素材，依据许可使用，保留作者与许可，不冒称原创。
- 对组合后的产品，可以对自己的原创部分主张权利，但不把第三方部分据为己有。
- 许可证不能保证上游绝无侵权或专利问题；选择可信来源并保留依据，能够降低风险，无法承诺无人投诉。

### 按当前偏好选择依赖

| 类别 | 当前处理原则 | 核查重点 |
| --- | --- | --- |
| 通用框架、工具库 | 优先采用来源可靠、维护正常且许可适合的现有实现 | 精确版本、MIT / BSD / Apache 等实际条款、传递依赖、版权声明与 NOTICE；宽松许可也有义务 |
| 字体、图标、基础素材 | 使用来源与许可明确的资源，不必全部自制 | 字体许可、图标包不同部分的许可、署名、修改和嵌入条件；可商用不等于独占 |
| 核心角色、标识、主视觉、角色设定 | 优先自主创作；必要时采用范围清楚的委托安排 | 创作记录、源文件、具体表达是否近似他人作品、授权链 |
| GPL / AGPL / LGPL / MPL 等组件 | 不是违法或劣质组件；按具体义务和产品架构评估 | 是否修改、链接或形成组合作品，如何交付，对应源码或替换等义务；不能一律按同一种规则处理 |
| 专有 SDK、在线 API、模型权重与音色 | 单独评估合同依赖和替换成本 | 软件许可与服务条款分开查，商业用途、用户内容处理、输出与分发权限、审查及收费要求 |
| 无许可、来源不明或条款矛盾的内容 | 当前策略是不新增到拟公开产品；已有部分列入替换清单 | 取得可核实授权，或以独立实现、自产素材、权属明确资源替换 |

MIT / BSD / Apache 常适合保留闭源商业选择，但仍应读具体版本与例外。CC0 资源也可能涉及肖像、商标等未被完整解决的权利，不能只看到标签就认定所有用途均无风险。

不要仅按“开源 / 不开源”判断：GPL 明确但业务不接受其义务，属于许可策略不匹配；无许可证的网图看似免费，反而可能没有可证明的使用依据。

### 每新增一个依赖，留下最小记录

1. 从官方仓库、官方网站或可信包分发源取得，记录名称、精确版本或提交号及来源。
2. 检查许可是否覆盖实际使用的代码、二进制、图片、模型、权重等，不能只看仓库首页标签。
3. 记录用途：仅构建工具、运行时导入、修改后嵌入、随安装包分发，还是调用外部服务。
4. 检查直接和传递依赖，记录需要保留的版权、许可、NOTICE、源码提供及其他条件。
5. 将条件落实到实际发布物；更新版本时复核许可变化，不只首次检查。

台账字段建议：名称｜版本/提交号｜作者/权利人｜来源｜许可原文位置｜使用位置｜修改情况｜分发方式｜需履行条件｜已留证据｜结论｜替代方案。

`pip-licenses`、`license-checker` 或 SBOM 工具用于辅助盘点，不是合规认证；可能漏掉手动复制代码、模型、素材及在线服务条款。NOTICE 文件也不能代替履行每项许可的实际要求。

### 自主替换的边界

- 依据公开的功能需求和有权使用的接口资料独立实现，可以保留自己的实现与设计记录；仍需留意具体协议、专利、商业秘密等限制。
- 不把他人源码交给 AI 改名、改写或翻译后称为自主开发；改写不自动消除原许可义务。
- “自己画”“重新画”也不自动摆脱对他人具体角色或构图的复制。一般风格不等于具体表达，但是否侵权要看实际作品，不能预先保证安全。
- 自制 Live2D 角色解决的是模型美术来源，使用 Cubism Core 仍需遵守其许可；改用自主渲染方案也要分别处理代码、格式和资源权利。
- 把 GPL 组件改成单独进程、独立插件或让用户下载，并不当然消除组合或分发问题，不能当作通用规避方案。

### 本项目的渐进替换顺序

1. 先记录现存疑点和功能调用位置，区分已证实问题、未确认事项、许可证明确但不适合未来商业路线的部分。
2. 优先把核心角色外形、立绘、主视觉和角色卡替换为有完整创作记录的自主内容。
3. 针对 Piper、Live2D Core / 模型 / 可扩展应用、语音权重和服务逐项选择：接受并履行许可、取得明确授权、替换实现，或暂不进入发布版。
4. 保留合规且适合业务的通用框架与工具库，把时间投入产品体验和真正需要控制的核心能力。
5. 接近展示或发布时再检查实际产物与 Git 历史；本轮不删除资源、不改索引、不重写历史、不变更产品许可。

私人自用不是对所有使用行为的统一免责；本地保留的存疑内容也要记录合法来源和允许用途，不因暂未发布就断言完全无风险。

## 8. 对外部建议的校正记录

对 Claude Code 意见的采纳范围：认可分层授权、保留创作证据、登记稳定版本和发布前清理；下列说法不作为决策依据。

- 未核实的“10 万行”不作为规模或原创性结论；求职价值主要看实际贡献、设计判断和完成度，不靠许可证或商标保证加分。
- AGPL 不等于“网络提供即分发”，也不能直接推断前后端全部受同一义务约束。
- Live2D Core 当前核查的相关限制在专有协议 v2.1 的 **5.3.2**，并非引用中的 5.6；不能将 Core 自身重许可为 GPL/AGPL，实际组合兼容性需单独判断，不能泛化为所有自有应用代码均不能开源。
- Live2D 素材协议的禁止转发条款有明确许可例外，Haru/Hiyori 应结合具体条件判断，不仅凭旧台账认定“一公开必然侵权”。未确认前不纳入发布物是处理策略，不是侵权定论。
- 后端并非全是宽松许可，已发现 Piper GPL；自动清单工具无法独立完成素材和服务合规核查。
- CLA 不一定要求转让版权，DCO 不自动授予商业重许可权；“修改权全部转让”等表述需要修正。
- OFL 的保留字体名称主要影响修改字体的命名，不是禁止用户正常使用原字体；具体以对应字体许可为准。
- 文档没有必要默认整体采用 CC BY / CC BY-SA，应先检查私人资料和第三方引用，再根据希望授予的权利选择范围。
