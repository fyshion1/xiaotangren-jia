# 小糖人之家 · 项目要求与设计方案

> 本文档是项目的唯一需求源。后续所有实现、AI 维护、版本迭代均以本文档为准。
> 更新规则：需求变更时先改本文档，再照文档实现；本文档同时作为喂给 AI 的固定上下文。
> 最后更新：2026-09-30

---

## 1. 项目定位

**一句话**：一个"小糖人专属"的本地优先、无审查的多模态 AI 聊天客户端，核心是小糖人角色（大诗音、小诗音、小白、小红薯头），并配有 Live2D / 3D 可视化形象。

**与 SillyTavern 的关系**：本项目不基于 SillyTavern（ST），而是**从零重写**。只复用"大模型 API"这一个能力，其余（前端 UI、后端、存储、多模态、可视化、记忆）全部自建。（背景：此前存在一个基于 ST 套壳方案的历史，仅作为背景，不在本项目中展开。）

---

## 2. 战略考量（为什么这样选）

### 2.1 从零重写，而非套壳 ST
- ST 前端是无框架的 jQuery/原生 DOM 拼字符串，嵌入 Live2D 会被其 DOM 刷新干扰，需用 MutationObserver/轮询硬扛，维护像"排雷"。
- ST 上游更新会破坏注入的 CSS/JS。
- 从零写：现代组件化代码（React+TS），AI 生成质量高、出错率低、返工少，正符合"后续基本 AI 维护"的诉求。
- 代价：需要自己补"聊天记录存储、流式解析、上下文裁剪、Token 计数"等基础能力 → 通过复用现成库/模板规避（见 §4）。

### 2.2 目标用户与使用方式
- 核心：**自己一个人用**，非商用。
- 前期：本地单机跑（现有 3050 4GB）。
- 后期：部署到自有 J1900 服务器 + 国外域名 + Cloudflare 穿透（好兄弟已验证稳定），实现多设备访问；但架构上不为此牺牲本地单人体验。
- 长远目标：即使 J1900 性能有限也尽量优化到能跑（不够再加预算）；**较长一段时间内主要在本地 3050 上开发**。

## 3. 核心功能清单（含优先级）

### 3.1 MVP（第一版，必须先跑通）
1. 文字聊天（流式输出、打字机效果、多路模型切换、无审查）
2. 看图（上传图片 → 多模态模型理解并回复）

### 3.2 第二阶段
3. 人设 / 世界书 / 越狱 + 记忆（三层 RAG，见 §9）—— **核心之一，紧跟 MVP**
4. 语音交互（ASR + TTS）—— 前期占位方案，毕设优化成果出来后替换内核（见 §6）
5. 生图（NSFW 支持）—— 四引擎插槽切换器：本地 ComfyUI / 云端 ComfyUI / 第三方生图 API / NovelAI（预留），见 §7

### 3.3 远期
6. Live2D 角色显示（说话/表情/简单触发动作）
7. 3D 角色接入（Blender 导出 VRM，见 §5.2）
8. 看视频（视频抽帧 / 音频转文本）
9. TTS 专属音色（GPT-SoVITS 等训练小糖人专属声音）

> 优先级原则：Live2D 是次要/加分项，仅保留接口，不阻塞主线；3D、视频、专属音色均不阻塞主线。

## 4. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | **React + TypeScript + Vite** | AI 维护最友好、资料最丰富、类型安全；适合大量非标准交互 |
| 前端样式 | Tailwind CSS | AI 生成 UI 收敛 |
| 后端 | **FastAPI（Python）** | 用户最熟 Python；AI 维护友好；Python 生态对 LLM/多模态/Whisper SDK 最全 |
| 后端流式 | SSE（Server-Sent Events） | 聊天流式输出标准做法 |
| 存储 | SQLite（聊天记录/配置）+ 向量库（记忆，见 §9） | 轻量、单人够用 |
| 模型接入 | 多路切换（见 §7） | 商业 API / 第三方无审查中转 / 本地 Ollama，统一走 OpenAI 兼容适配器 |
| 可视化 | pixi-live2d-display（Live2D）、three.js + @pixiv/three-vrm（3D） | 见 §5 |
| 语音 | sherpa-onnx（ASR/TTS/唤醒）、piper + edge-tts（TTS，都要、留切换） | 见 §6 |
| 包管理/构建 | 前端 pnpm；后端 uv；启动脚本 + Docker | 见 §12 |

**规避"轮子工程"的手段**：不与 ST 耦合并自建，但也不重复造轮子——聊天流式/上下文管理复用成熟库，把精力集中在"小糖人专属可视化 + 多模态 + 记忆 + 越狱"上。

## 5. 可视化：Live2D 与 3D

### 5.1 Live2D（远期，加分项）
- 库：官方 `pixi-live2d-display`（性能好、支持动作触发/表情切换）。
- 映射：大诗音说话 → 切换到大诗音模型；特定角色说话 → 触发对应动作（如点头摇脑）。

### 5.2 3D（Blender → VRM，后续接入）
- 目标导出格式：**VRM**（vTuber 标准，自带人形骨骼/表情 BlendShape/物理/视线）。
- 模型状态：暂无，用户会用 Blender 后期建模（会建）。
- Blender 侧三件事：建模 + Humanoid 绑骨 → 做表情 BlendShape（`a i u e o` 口型 + 表情）→ `VRM_Addon_for_Blender` 导出 `.vrm`。
- 前端：`three.js` + `@pixiv/three-vrm` 加载。

### 5.3 关键抽象：统一 Avatar 接口
让 Live2D 和 3D "加分项可随时换"，定义统一角色渲染接口：

```
Avatar（抽象接口）
├── 说话时张嘴 / 切换表情
├── 触发指定动作（摸头 / 点头 / 吃惊）
└── 站到某位置 / 场景
      ↑ 实现
  ┌────────────────┬──────────────┐
  Live2DAvatar(远期)  VRMAvatar(以后)
```

触发引擎（小糖人说话 → 张嘴/点头）是通用的，不关心底层渲染是 Live2D 还是 3D；两者可共存切换。

## 6. 语音交互（与毕设联动）

核心认知：本项目语音交互与毕设（校园无人车端侧语音）是**同一个引擎**——都是"低算力 + 嘈杂环境 + 轻量 + 低延迟 + 流式 + 鲁棒"约束。毕设优化成果直接替换过来，本项目作为毕设的"个人端侧落地验证场"，双向迁移。

> 注：毕设当前处于选题阶段，本文档不展开毕设本身，只约定本项目语音层的架构与占位方案，正式实现等毕设推进后再细化。

### 6.1 语音层抽象（Provider 接口）
```
语音层（预留 Provider 接口，内核可替换）
├── ASR 接口   → 占位: sherpa-onnx / Whisper  → 毕设优化引擎替换
├── TTS 接口   → 占位: piper(全本地) + edge-tts(省心)，都要、留切换按钮 → 以后换专属音色
└── 唤醒/门控  → 占位: Silero VAD / sherpa-onnx KWS("小糖人"唤醒词) → 毕设降噪+门控
```

### 6.2 关键锚点：sherpa-onnx
一站式边缘语音工具箱（ASR/TTS/唤醒词/流式/量化，C++/Python 双端，专为 ARM/低算力设计）。**同时服务毕设小车与本项目**，两者共用同一套 API，迁移 = 复制粘贴。

### 6.3 TTS 约定（重点，与毕设强相关）
- **piper + edge-tts 都要，前端留切换按钮**：piper 全本地（毕设做全本地轻量语音识别优化的直接参考）；edge-tts 在线（音质稳、最省心、依赖网络）作为备选。
- **必须留切换接口**，后面要换 GPT-SoVITS 等专属音色。

## 7. 模型接入矩阵（多路切换 / 无审查方案）

前端提供"模型来源"切换，后端做统一代理转发（解决 CORS + 隐藏 API Key），**统一走 OpenAI 兼容适配器**（中转/商业/Ollama 的 OpenAI 兼容端点都覆盖）：

| 来源 | 用途 | 备注 |
|---|---|---|
| 商业 API（OpenAI/Claude/Gemini） | 日常对话、vision 最稳 | **NSFW 会被封**，需按需分流 |
| 第三方无审查中转 API | NSFW 对话 / NSFW 生图 | 购买中转 key，即插即用，无显卡要求 |
| 本地 Ollama（Qwen/GLM/Llama） | 完全离线无审查 | 受 3050 4GB 限制，效果弱于商业模型 |

- **多模态（看图）**：图片 → Base64 → 传给支持 vision 的模型（Gemini/Claude/GPT-4o/本地 VLM）。
- **生图（NSFW）**：四个**可插拔引擎插槽**，前端一键切换，后端按当前选择分派。**本地与云端 ComfyUI 是同一个 HTTP 协议**（`POST /prompt` → 轮询 `GET /history/{id}` → `GET /view?filename=...`），所以共用同一套客户端实现（`services/comfyui.py`），只是 `base_url` 不同——不是两套代码。

  | 引擎 id | 名称 | 说明 | ready 判定 |
  |---|---|---|---|
  | `local` | 本地 ComfyUI | 3050 4GB 本地跑，免费无限，吃显存 | `COMFYUI_URL` 的 `/system_stats` 可达 |
  | `cloud` | 云端 ComfyUI（CNB 等） | 同协议，只是地址不同（SSH 端口转发后的地址） | `COMFYUI_CLOUD_URL` 的 `/system_stats` 可达 |
  | `thirdparty` | 第三方生图 API | 任意 OpenAI 兼容 `/images/generations` 中转 | 配了 `IMAGE_BASE_URL` + `MODEL_IMAGE` |
  | `novelai` | NovelAI（预留插槽） | 协议**不兼容** OpenAI，需独立适配器，本轮未实接 | 配了 `NOVELAI_URL` + `NOVELAI_API_KEY` |

  - 出图参数：提示词、负向提示词、尺寸、张数（上限 4）、步数、CFG、seed；工作流里没有的输入就不注入，留空即用工作流自带值。
  - 出图一律落到**附件库**（`source="generated"`，见 §15.1），返回 `{orig, thumb, id}`，前端不必分支；再手动 ⭐ 存入画廊（§9.4）。
  - **外观提示词拼装**：从当前会话在场角色的**当前形态**（§17）取外貌词条自动拼一句填进可编辑的提示词框；用户手改的内容不会被覆盖（脏跟踪按 `${charId}:${formId}`），旁边有「自动拼装外貌」开关和「↺ 重置」按钮。
  - **云端方案仍在逐个试**（2026-10 现状）：CNB 按核数计费（¥0.5/核时×核数）实测不合算；vast.ai 需信用卡暂不可用；AutoDL 明令禁止 NSFW；NovelAI 与本地 3050 跑无审查模型待试。**引擎抽象先做扎实，用户试出哪个就填哪个地址，零改代码。**
  - 腾讯云云端用 VSCode Remote-SSH 控制（免费额度已取消，见上）。

### 7.1 双通道（常规 / 无审查）——前端配置形态

上面三种来源，落到前端是**两条并列的通道**，聊天页头部一键切换：

- **常规通道**：日常对话/看图最稳的商业 API（如 Gemini）。NSFW 会被封。
- **无审查通道**：单独配一份 base_url / api_key / chat 模型 / vision 模型，指向第三方无审查中转或本地无审查 Ollama（abliterated 模型）。

约定：
- 两条通道**各自独立**存凭据，同存于前端配置里；无审查通道的字段**留空即回退常规通道**（可只填地址/模型，key 复用同一把）。
- 切换即作用于所有模型调用：聊天、看图、自动记忆提炼、画廊"自动描述"；**生图本轮仍走常规通道**（无审查生图留后续）。
- 后端 **不改路由层**：`providers/openai.py` 是无状态的（每次调用显式传 base_url/api_key/model），路由层只负责把请求透传；前端按当前通道解析出实际路由参数即可。
- 后端只多接一个 `uncensored` 布尔：为真时，System Prompt 末尾额外追加一条"无审查通道专属规则"（见 §6.x 越狱设置的双文本框）。

## 8. 会话与角色：群聊「家」模型（核心设计）

### 8.1 世界观设定
- 4 个小糖人：大诗音、小诗音、小白、小红薯头。
- 加上**大老大**（用户本人，见 §8.5），共 5 张角色卡。
- 她们**互相认识**，大多数时间在一起（群聊），偶尔也有私聊；有私人空间，但彼此界限不明显。
- 因此数据模型不是"每个角色一套孤立人设"，而是一个"家"。

### 8.2 数据模型
- **一个"家"**（一个应用实例）= 一群角色 + 共享记忆 + 各角色个人记忆。
- **会话 = 一或多个"在场角色"**：
  - 群聊：多角色在场（默认四位齐全，可勾选谁在场）。
  - 私聊：只留一位在场——复用同一套"会话/在场角色"模型，天然实现，不单独复杂化。
- 每个角色拥有：人设、个人记忆、专属 Live2D/3D 形象（后两者远期）。

### 8.3 群聊引擎：单 LLM 多角色 + 留升级口
- **默认方案**：单 LLM 多角色。用一段"舞台/多人剧场"规则让模型自己轮流分饰多角（低成本、最稳定、与用户惯用的 Gemini"一人分饰多角"模式一致）。
- **预留升级**：把"角色调度"抽成独立模块，将来可无缝换 **多 Agent 调度**（每个小糖人独立上下文/记忆，调度器决定谁说话）。
  - 多 Agent 的代价已评估：成本几乎翻倍（每角色独立调用）、实现需调度器 + 独立上下文管理，复杂度高一个量级——故当前不采用，仅留接口。

### 8.4 形态（§17）：一个角色多套人设，id 不变
- 一个人物可以有多套**形态**模板（如大诗音的「第一形态 · 粉发」/「第二形态 · 紫发」）。形态不是换皮肤：**除记忆外全部词条都可覆盖**（外貌、性格、服装、乃至「关于」提示词本身），因为性格随形态变化是预期内的。
- **硬约束：角色 id 永远不变**。会话 id 是 `single-<charId>`、个人记忆按 `char_id` 分桶 —— 一旦形态改了 id，单聊历史与个人记忆就会"孤儿化"。
- 因此形态**只覆盖档案词条，不碰记忆**；换形态 = 同一个人换了副模样，记忆照旧。

### 8.5 大老大：用户自己的角色卡
- 大老大 = **用户本人**（`id: dalaoda`）。他和其他小糖人一样拥有完整档案：介绍页、立绘、头像、形态、专属画廊 —— 但不参与"被扮演"。
- **形态**：两套（`日常` / `战斗模式`），与 §8.4 同一套机制，id 不变。
- **⚠ 硬约定：大老大不进群聊的默认在场角色**。单 LLM 分饰多角时，若把用户自己列进"在场角色"，模型会以为要替用户说话，与用户亲手发的消息打架。默认阵容仍是四位小糖人。
  - 若将来确实想让她在场（比如做"旁观者旁白"之类的玩法），改群聊默认 `characterIds` 即可，不动数据结构。
- **补种约定**：`init_db()` 采用**逐条幂等补种**（`INSERT ... ON CONFLICT(id) DO NOTHING`）。老库升级时会自动多出大老大，但用户已经手动改过的角色**绝不被覆盖** —— 加新角色从此不用改代码。

### 8.6 立绘与头像：浏览器选图上传
- **两个字段**（都在 `CharacterProfile` 里，都存 URL）：
  - `portrait` —— 立绘（静态图 / **GIF** 都吃），介绍页大图
  - `avatar` —— 头像（正方图最佳），聊天气泡、会话列表、群聊分段说话人用；**留空则回退 emoji**
- **上传方式**：编辑器里给这两个字段各配一组「预览格 + URL 输入框 + 🖼 选择本地图片 + 清空」。选图走 `FileReader → dataURL → POST /api/attachments`（`session_id="characters"`）落盘，拿回 URL 写回字段 —— **和画廊上传同一条附件管道**。外链 URL 也照旧能手填。
  - 两个字段共用一个内部小组件（`ImageField`），不复制两份。
- **头像渲染统一走 `Avatar` 抽象**：有 `avatar` 显示图、没有显示 emoji。接入四处：聊天头部缩略头像、**群聊分段说话人（头像 + 名字，QQ 式）**、助手气泡上方的名字行、会话列表。
  - ⚠ 群聊分段的说话人是**名字字符串**（`segmentGroupReply` 解析出来的），要按名字反查角色拿 avatar；匹配不到就退回名字首字。
- **Live2D / 3D 形象本轮不做**（§5 远期），素材先攒着。

## 9. 人设 / 记忆 / 越狱（核心之一，MVP 后做）

### 9.1 人设 + 世界书 + 越狱 Prompt 组装引擎
- **非常需要，是核心之一**：为每个小糖人维护人设、世界书（World Info）、以及无审查越狱 System Prompt。
- 后端需内置一套 **Prompt 组装引擎**（人设 + 世界书 + 记忆检索结果 + 越狱规则 → 组装成最终请求）。
- MVP 先不做，但架构从第一天起预留（影响后端 Prompt 组装与存储设计）。

### 9.2 记忆三层（对齐"家"模型，短期 + 长期）
| 层 | 内容 | 实现 | 生命周期 |
|---|---|---|---|
| **家记忆（共享）** | 共同经历：一起吃饭/玩闹、重要节日等 | 向量库 `home` 集合 | 长期 |
| **个人记忆** | 各角色私密记忆：秘密、偏好 | 向量库按角色分集合 | 长期 |
| **会话上下文** | 本次聊天最近 N 轮 | 直接进上下文 | 短期 |

**机制**：每条消息发出前，后端做一次"记忆检索"——拿当前消息（+最近几轮）做 query，从家记忆 + 在场角色的个人记忆检索相关片段，连同关系摘要/人物档案、人设、越狱规则一起组装进 System Prompt。

> **澄清一个常见误解**：流传的"酒馆实时学习/训练角色"插件，本质是 **RAG（向量检索注入）**，不是微调——模型权重没变，只是"每次被提醒更多过去的片段"。
> 本项目采用 **RAG，不用微调**。理由：微调是离线昂贵的一次性动作，会焊死风格，且不利于多角色 + 多路模型切换；RAG 灵活、可随时换模型、贴合"越聊越懂我"的真实需求。

#### 9.2.1 Embedding 抽象
- 做 **Embedding Provider 接口**，两个实现：**本地小模型**（默认，sentence-transformers + 中文 `bge-small-zh` 之类，约 100–130MB，CPU 可跑，离线、贴合本地优先 + J1900）+ **云端/中转 `/v1/embeddings`**（零本地算力、依赖网络）。
- 默认走本地；配置里可切到云端。两者产出的向量口径不同，**换 engine 后需重建向量库索引**（见 §16.6 避坑）。
- embedding 模型文件不进 git，提供下载脚本（同 piper 思路）。
- 各记忆条目的向量与原文一起落库，检索时做余弦相似度 topk。

#### 9.2.2 分桶与注入规则（私聊保密的核心）
- 一条记忆 **落库时必须打标**，决定它进哪个桶：
  - **群聊产生** → 默认进 **家记忆**（共享）。
  - **私聊产生** → 默认进 **那个人的个人记忆**。
  - **手动记忆** → 让用户可选「存到谁的记忆 / 家记忆」（顺带覆盖"私聊里冒出全家都知道的事"这种特例）。
- **检索只注入在场者**：
  - 群聊（四人在场）→ 注入 家记忆 + 四位各自个人记忆。
  - 私聊（只 TA 在场）→ 注入 家记忆 + TA 个人记忆。
- 效果（自动成立）：今天和小诗音私聊去买东西 → 只进小诗音个人记忆 → 小白私聊不知道、群聊里小诗音"记得"而其他三人不知道。**无需额外发明，靠"打标 + 按在场注入"两条规则即可。**

#### 9.2.3 检索粒度
- 检索 query = 当前消息 + 最近 N 轮拼接，分别对家记忆与在场者个人记忆做 topk，各自控制条数（防塞爆上下文），组装进 System Prompt 的相关片段区域。

### 9.3 记忆「什么值得记」与「怎么记」
- **手动**：你点"记住这条"（最可控，贴合"我和你之间才知道的事"）。
- **自动**：规则触发（出现"记得/以后/约定"等词，或对话出现情感浓烈/长期信息时，让 LLM 提炼成一条记忆条目存库）。
- 两者都留，MVP 后做。

### 9.4 画廊与「照片记忆」+ 生图认人（远期）
- **画廊** = 你主动保留的重要图片（不是"只读"的临时文件）。聊天图片气泡提供「⭐ 存入画廊」；画廊图 = 图片文件 + 一段文字描述。
- **照片记忆（A 方案，默认）**：把画廊图的文字描述当一条记忆走 §9.2 的 embedding/RAG；聊到相关话题时注入"你有一张照片：<描述>"。每条画廊记忆带「是否进小糖人记忆」勾选（默认进，可关闭某些过于私密的）。
- **照片记忆（B 方案，留口子）**：多模态 embedding（中文 CLIP），让图片和文字进同一向量空间，聊天文字能直接"检索到图"。先只留 Provider 接口占位，默认不用。
- **画廊 → LoRA → 生图认人（思路，排期靠后）**：
  - 可行性：可行；画廊天然就是训练集。同一个角色 15~30 张起步，标签复用"该图文字描述"或 WD14 自动打标。
  - 三条路：**LoRA 微调**（kohya_ss/sd-scripts，最正宗，3050 4GB 可训 SD1.5 LoRA，SDXL 勉强；腾讯云免费 4h/天训也合适）→ **IP-Adapter/InstantID（免训练，1~10 张参考图）** → **LoRA 打底 + IP-Adapter 换装/表情**（推荐节奏）。
  - 前置依赖：生图切换器先接实机 ComfyUI → 画廊攒够图 → 再训 LoRA。顺序不可乱。

#### 9.4.1 画廊归属：私人的，不是公共的
- **问题**：原设计里画廊不分人 —— 在任何一个角色的介绍页翻画廊，看到的都是同一堆图。但"和大诗音的画廊"和"和小诗音的画廊"本该是两回事。
- **字段**：`gallery.owner TEXT NOT NULL DEFAULT ''`。
  - `owner = ''` → **家 · 共用**（大家共同的回忆，进「糖人小窝」）
  - `owner = <charId>` → **该角色专属**（只有我和她）
  - 用空串而非 `NULL`，与 `memories.char_id` 的既有约定保持一致（§9.2.2）。
- **自动归属规则**（前端一处推导，后端不感知）：
  - `session.kind === 'single'` → `owner = characterIds[0]`
  - 群聊 / 导入会话 → `owner = ''`（家共用）
  - 聊天里点 ⭐、生图浮层点 ⭐，都按这条规则落归属。规则只写在 `frontend/src/lib/owner.ts` 一处。
- **可手改**：画廊面板里每张图带一个归属下拉（「家 · 共用 / 大诗音 / 小诗音 / …」），改完即时 `PATCH`。**不做自动识别** —— 用户明确说"我会自己手动分类"。
- **自定义上传**：不再只能"发出去再收藏"。画廊面板有「＋ 上传图片」，选本地文件 → `POST /api/attachments`（`session_id="gallery"`）落盘 → `POST /api/gallery` 带 `owner` 入库。别处生的图也能进画廊，成为记忆的一部分。**后端零新代码**，复用既有附件管道两步走。
- **照片记忆跟着归属走**：`owner === ''` → `bucket='home', char_id=''`；`owner !== ''` → `bucket='personal', char_id=owner`。所以私人画廊的描述只有她本人在场时才检索得到（§9.2.2 的私聊保密）。
  - **改了归属要重建记忆**：`update_gallery` 收到 owner 变化时，若该图"进记忆"，删掉旧记忆按新桶重建（与"描述改了要重建"同一套路径）。
- **查看范围**：角色介绍页下方的画廊 = 该角色的专属；「糖人小窝」= 家共用；聊天里的 🖼 浮层 = 全量（带归属筛选和手改下拉，是"整理"的地方）。

### 9.5 提示词词典与预览图（方案已定，另开一轮实现）
- **提示词词典**：中文 → 英文标签（映射）的表，**可开关**（有些模型吃中文某些只吃英文），**用户可扩展**，**按类别分**（衣服 / 鞋子 / 姿势 / 场景…）。存**后端 SQLite**（不是 localStorage）—— 因为要经常被引用、要跨设备、要跟着 git 之外的库走。
  - 表结构草案：`prompt_tags(tag_id, category, name_zh, name_en, preview_url, user_added, created_at)` + CRUD 路由 `/api/prompt-tags`。
  - 思路来源：ComfyUI 社区插件里的"提示词库"（点一下就插到正向提示词里），复用性高，以后**也有打算做成自己的 ComfyUI 插件**。
- **预览图（两级：大类 / 小类）**：
  - **小类** = 用户**手动裁剪上传**的截图（例如「镂空红底高跟鞋」），存 `prompt_tags.preview_url`。
  - **大类** = 前端 canvas 把若干小类图**拼成一张总览拼贴图**（例如「高跟鞋」）。
  - **两条路都保留**：手动优先；**自动生成预览（拿生图模型跑一张当预览）只留一个接口/钩子**，不实现。
  - 理由（用户原话意）：有时需要**对比不同模型对同一提示词的反应**，手动截图与自动生成各有场景。
- **本轮不做**：词典与预览图都不在生图这一轮，等引擎实机接好、提示词真正用起来再做。

### 9.6 糖人小窝（介绍页左侧的家门 + 顶部导航第三个按钮）
- **定位**：全家的**共同回忆**与以后要接的**共同玩法**入口。每一位小糖人的专属画廊在各自的角色介绍页里；小窝只放"家 · 共用"的那份。
- **入口两处**（都通到同一个视图）：
  - 顶部导航第三个按钮「🏠 糖人小窝」
  - **角色介绍页成员切换行最左边**那个按钮（用户原话："角色介绍左边看看能不能再开一个按钮"）
- **内容**：
  - **共同回忆 · 画廊** —— 复用 `GalleryGrid`，传 `owner=''`，只看家共用的。
  - **占位卡片**（点击弹「规划中」，**不做假功能**）：
    - 🎮 一起玩的小游戏（谁是卧底 / 你画我猜 / 猜谜）
    - 🏡 互动小家（Unity 渲染的可走动三维场景）
  - 记忆面板不在这里重复（已在聊天页右栏）。
- **实现约束**：`App.tsx` 的 `View` 从 `'home' | 'chat'` 扩为 `'home' | 'chat' | 'nest'`；新组件 `NestView.tsx` 无状态、无新依赖，跟 `HomeView` 一个体量。

## 15. 聊天记录持久化与附件存储

> 对齐 QQ / Gemini 的通行做法，抽象成本项目的存储方案。核心：**文本进库、媒体进文件、游标分页、缩略图永久而原图可清理**。

### 15.1 存储分层
- **消息文本 / 元数据 → SQLite**（现有 `xiaotangren.db` 加 `messages` 表）。
  - 字段：`id`、`session_id`、`role`、`content`(文本)、`image`(附件引用路径，可空)、`kind`/`segments`(群聊分段，JSON)、`seq`(单调自增，作游标)。
- **图片媒体 → 绝不存 BLOB**，落盘到 `backend/data/attachments/{session}/{hash}.jpg`，数据库只存引用路径。
  - 每张图 = 原图 + 缩略图；消息气泡先看缩略图，点开才加载原图。
- **来源统一**：用户上传图（看图接口）与 API 生图走同一条"附件落盘 + 存引用"管道，仅差 `source` 标记（`upload` / `generated`），便于分开清理/展示。

### 15.2 分页
- 游标分页（cursor），不用 offset：`GET /api/messages?session=xx&before=<seq>&limit=30`。
- 启动预载最近 30 条；向上滚到顶再按游标拉更早。**不做全量加载**。
- 每个会话（群聊 + 各大私聊）独立历史；发一条存一条（流结束落库）。

### 15.3 原图空间回收
- 缩略图**永久保留**（保证回看体验）；原图可按需清理。
- 提供「清理原图」入口：按日期 / 会话 / 全部，只删原图文件、保留缩略图（删后点大图降级为缩略图）。
- 可选 TTL 自动过期（学微信），开关可配。

### 15.4 单条 / 批量删除与附件回收（"真删"）
- **入口**：聊天页消息右键 → 「删除这条」/「多选…」；多选模式下每条消息左侧出复选框，顶部浮出操作栏「已选 N 条 · 删除 · 取消」。**只有用户自己发的、且已落库的消息能删**（助手回复不提供删除入口）。
- **真删语义**（用户明确要求："这里的删掉是真删，包括发出去的图片"）：
  1. 先删消息行（`messages`）
  2. 图片若**再无幸存消息引用**，连带删掉画廊里对应收藏（及其照片记忆）与磁盘上的原图 / 缩略图文件
  3. 返回 `{deleted, files_removed, gallery_removed}`，`POST /api/messages/delete-preview` 提供只读预检，前端确认框如实写出「N 条记录 + M 张图片 + 画廊 K 张」
- **⚠ 共享图保护（最容易写错的地方）**：删文件**之前**必须查一次幸存引用 —— `list_messages_by_image(orig, exclude_ids=本次删除的 id 集合)`。还有别的消息引用它 → **只删消息记录、保留文件**；否则会把另一条没被选中的消息的图也弄挂。
- **存量数据兼容**：老画廊记录的 `message_id` 存的是消息序号字符串而非 `m-<hex>` 主键。级联匹配用**双条件** —— `message_id = <dbId>` **或** `orig = <该消息的图片 URL>`，两条都命中。
- **接口**：`DELETE /api/messages/{message_id}`（单条）、`POST /api/messages/delete`（批量，body `{ids: [...]}`）。原有的 `DELETE /api/messages?session=`（清空整个会话）保留不动。
- **实现约束**：批量必须"一次 SELECT 取回 + 一次 DELETE"，不要循环单条调用；引用检查与级联逻辑抽在 `services/cleanup.py`，路由层只做参数校验。
- **交互约定**：确认框用 `window.confirm`（与项目里既有先例一致，不新造弹窗组件）；**流式生成中禁用删除**。

## 16. 避坑点（踩坑记录）

> 开发中踩过的坑，按「现象 → 成因 → 解决思路」简要记录。只记思路，不记代码，供后续重做同类能力时少走弯路。

### 16.1 打字机偶发「一次吐一大块字」
- **现象**：流式输出偶尔十几个字一起蹦出来，不像逐字流水。
- **成因**：模型/中转的 SSE 分块不均匀——一个网络 chunk 里可能带很多 token；前端「收到一块就整块贴上去渲染」就会一大坨。
- **思路**：前端加一层平滑缓冲：先把后端吐的文本缓存，再按固定节拍（几十 ms）少量逐字渲染；积压多时适当加快出字速度，避免拖尾过久。

### 16.2 换中转站后文字聊天返回空白
- **现象**：模型没任何输出，前端一片空，无从排查。
- **成因**：① 中转站之间模型名容忍度不同（旧站模型名到新站直接 `model_not_found`/503）；② 部分中转会在 200 的流里才塞 error 对象、且无 choices，旧解析把它当「正常结束」→ 静默空屏。
- **思路**：把上游错误照实透出到前端（别吞掉）；瞬时错误（429/5xx）自动重试，致命错误（模型名/密钥错）直接显示原因。

### 16.3 看图时图片格式与中转站不适配
- **现象**：识图突然不可用。
- **成因**：不同中转对图片 content 格式要求不同（data URL vs 裸 base64），裸 base64 会被部分站打成 400「API key not valid」这类误导性报错。
- **思路**：统一用 data URL（`data:image/...;base64,...`）；每次换站先 `GET /v1/models` 确认可用模型名，再用 data URL / 裸 base64 各打一张图探格式（别用 OCR/猜）。

### 16.4 语音朗读多条并行、无法停止
- **现象**：快速多点「朗读」会多条语音同时响，且没有办法停下当前这条。
- **成因**：播放函数在 fetch→blob 之间有一段异步等待窗口；快速点击时每次都新建独立 `Audio` 并各自 `play()`，且旧代码只有 `pause`、没有「清除 + 摘回调」的完整停止动作。
- **思路**：单一音频控制器 + 请求令牌防竞态（每次播放发新令牌，在途旧请求作废丢弃）+ 显式 stop（pause + seek 0 + revoke URL + 摘回调）。注意 edge-tts 是「整段 MP3 合成后播放」，前端 stop 只能停住正在播的、没法逐字流式打断；要「边合成边停」得等换流式 TTS（GPT-SoVITS 那类）。

### 16.5 piper 本地音色不在仓库里
- **现象**：换机器 / 新 clone 后 piper 引擎没有音色可用。
- **成因**：piper 音色是 ~60MB/个 的 onnx 大文件，且官方仓库有删除音色的情况（如 `hui_female` 已删），故不入 git（已 gitignore）。
- **思路**：提供下载脚本 `download_piper_voices.bat` / `.sh`（默认 hf-mirror，可设 `PIPER_MIRROR` 换源）；启动前跑一次把音色下到 `backend/data/tts/piper/`。别忘了把「音色需单独下载」写进 README。

### 16.6 embedding 换引擎后向量口径不一致
- **现象**：本地小模型 embedding 与云端 `/v1/embeddings` 产出的向量放在一起，检索时余弦相似度会乱掉（不同模型向量空间不同，距离不可比）。
- **成因**：embedding 模型一变，向量维度/数值分布完全不同，跨模型的向量不可混用。
- **思路**：向量库要**记录当前 embedding engine**；切换 engine 时提示需重建索引（重跑一次全量 embed 落库），或直接分库/分集合隔离。默认本地模型，别在运行中静默换 engine。

### 16.7 本地 embedding 模型文件不在仓库里
- **现象**：新 clone 后记忆 RAG 无 embedding 模型可用、检索失败。
- **成因**：embedding 模型 ~100MB+，不入 git（同 piper 思路）。
- **思路**：提供下载脚本，把模型下到 `backend/data/models/embedding/`；启动时若无模型则打印「先跑下载脚本」提示，并回退到云端 embedding（若配了）或提示配置。

### 16.8 手机 / 局域网打开前端「全挤在一起」
- **现象**：手机浏览器打开 `http://<局域网IP>:5173`，聊天页布局塌陷、所有内容挤在一起；电脑 `localhost` 正常。
- **成因**：① 手机访问时浏览器**默认缩放**（`<meta viewport>` 缺 `user-scalable=no` / 初始缩放 >1 导致布局 viewport 失效）；② 三栏布局用固定 `w-[230px]/[240px]` + `max-w-[72%]`，在窄屏幕下宽度换算失效，flex 项被挤扁。
- **思路**：① 补 `viewport` meta（`width=device-width, initial-scale=1.0, user-scalable=no`）；② 聊天区改为**移动优先**：窄屏时侧栏收成**底部 Tab**（会话 / 聊天 / 状态，一次只显示一栏），桌面端 `md:` 仍三栏并排；气泡 `max-w` 窄屏 85%、`sm:` 起才 72%，字体/按钮放大到手机可点；③ 启动脚本只打印 `10.x` 局域网地址，过滤掉 `169.254.x.x`（APIPA）和 `172.x` 虚拟网卡段。


### 16.9 刷新 / 后台切回后「聊天记录没了」（其实一直在库里）
- **现象**：消息发出去后在库里能查到（`backend/data/xiaotangren.db` 的 `messages` 表有记录），但**刷新浏览器、或手机上后台切走再切回**，聊天页就空了；一直待在页面上、不刷新则正常。
- **成因**：**载入路径**被 React StrictMode 的 effect 双调用「吃掉」了（`ChatView.tsx` 首次载入历史的 `useEffect`）。React 18 开发模式下 effect 会 **setup → cleanup → setup** 走两遍：第一遍 `loadedRef.add(id)` 并发出 `loadMessages` 请求，紧接着 cleanup 把 `cancelled = true`；第二遍因 `loadedRef` 已命中直接 `return`、不再发请求。于是第一遍的响应回来时看到 `cancelled === true`，结果被丢弃 —— 历史**永远**填不进界面。第二遍又因去重标记不再重试，刷新 / 切回（移动端常被系统回收页面而重载）就表现为「记录没了」。
  - 注意：这跟**写入**没关系。落库是 fire-and-forget 的 `POST /api/messages`，一直是成功的（库里那 15 条就是证据）；坏的是**读出来渲染**这一步。
- **思路**：① 载入 effect 里**去掉 cleanup 的 `cancelled` 丢弃**（StrictMode 双调用下标记必须靠 `loadedRef` 去重，不能靠 cleanup 取消）；② 载入结果与本地未落库消息（`seq == null`）**合并**而非整体替换，避免「载入期间刚发的那条」被历史覆盖；③ `saveMessage` 失败不再静默吞掉，`console.warn` 留痕（以前后端没起也一声不吭，误以为已存）。
- **教训**：给「只跑一次」的 effect 加 `cancelled` 取消时，务必确认它不会被 StrictMode 的 cleanup + 去重 ref 组合打成「永远取消」。



### 16.10 陈旧配置清除会「吞掉」无审查通道已填的字段
- **现象**：配好无审查通道（地址 / key / 模型）后，前端配置的陈旧值清除逻辑一旦命中，**整份配置被重置为默认**，无审查通道那几个字段跟着一起没了，用户得重填。
- **成因**：`ChatView.tsx` 的 `loadConfig` 里有一段"过时配置清理"：发现旧的 baseUrl / 模型名已废弃时，直接 `return DEFAULT_CONFIG`（裸默认对象）。而 `DEFAULT_CONFIG` 里 `uncensored*` 全是空串 —— 于是新通道的字段被当成"不存在的旧键"一并丢弃。
- **思路**：清理逻辑**不再返回裸默认对象**，改为返回「在新默认基础上、只覆盖被判定为陈旧的那几个字段」的合并对象；并且 `uncensoredBaseUrl` 也纳入陈旧判定，避免它指向已废弃的地址时被漏掉。原则：**清理只该动它明确判定为陈旧的那几个键，不该整份重置**。
- **教训**：凡是"检测到坏数据就重置"的兜底逻辑，一旦配置对象新增字段就会误伤 —— 兜底要按字段做，不要按整体做。

### 16.11 不再调用网络搜索工具（环境限制）
- **现象**：会话里调用网络搜索/联网工具会被环境直接阻断，白等一轮。
- **成因**：当前运行环境不允许该工具出网。
- **思路**：**不要再尝试调用网络搜索工具**。需要外部资料（官方文档、API 说明、密钥、配置）时**直接向用户索要**，用户手上通常有（例如 `doc/` 下已放 CNB 官方文档）。**不要靠 OCR、不要靠猜**去替代真实资料。

### 16.12 本地与云端 ComfyUI 是同一个协议（别写两套）
- **现象**：一开始容易把"本地 ComfyUI"和"云端 ComfyUI（CNB 等）"当成两条独立通道去写，各写一套客户端。
- **成因**：误以为云端是另一种服务。实际上两者的 HTTP 接口**完全一致**：`POST /prompt` 提交 → 轮询 `GET /history/{prompt_id}` → `GET /view?filename=&subfolder=&type=output` 取图；命脉探针都是 `GET /system_stats`。
- **思路**：**一套客户端 + 两个 base_url**。`services/comfyui.py` 无状态、每次显式传 `base_url`；路由层只按 `local` / `cloud` 决定读 `COMFYUI_URL` 还是 `COMFYUI_CLOUD_URL`。**新增云端只是填一个地址，零改代码。**

### 16.13 ComfyUI 客户端三个必踩的坑
- **① 超时分层**：ComfyUI 出图是"提交后异步执行"，要轮询。若照抄 `providers/openai.py` 的 `httpx.Timeout(300.0)` 长读超时，实例卡住时会整整挂满 5 分钟且无法中途收手。
  - **思路**：单次请求用**短超时**（连接 10s / 读取 60s），**轮询不靠长读超时**，而是"短超时请求 + 外层 `deadline` 累计"，总预算由 `COMFYUI_TIMEOUT`（默认 180s）卡住；单次抖动（`httpx.HTTPError`）忽略后继续轮询。
- **② `n>1` 必须递增 seed**：ComfyUI 对**相同的 seed + prompt** 会返回**同一张图**，批量出图若只改 `n` 是无效的（它没有 `n` 参数）。
  - **思路**：逐张重提交，每张 `seed = base_seed + i`，`n` 上限 `min(n, 4)`（本机 3050 4GB 也吃不消更多）。注意节点里可能是 `seed` 也可能是 `noise_seed`（`KSamplerAdvanced`），两者都要处理。
- **③ 节点定位按拓扑，不按 id**：用户一定会自己改工作流（换模型、加 LoRA、换采样器），**写死节点 id 必崩**。
  - **思路**：顺着连线找——正向提示词 = `KSampler.inputs.positive` 指向的 `CLIPTextEncode`；负向 = `.inputs.negative`；seed/steps/cfg 在 `KSampler`/`KSamplerAdvanced`；宽高在 `sampler.inputs.latent_image` 指向的 `EmptyLatentImage`；出图 = `SaveImage`/`PreviewImage`。三级降级查找，**全失败时把扫到的 `class_type` 集合原样报错**（§16.2：不吞上游错误）。
  - 配套：示例工作流放 `backend/examples/comfyui/`（**不能放 `backend/data/`**，那里整个 gitignore），并在 README 写清"如何在 ComfyUI 里 `Export (API)` 导出 API 格式"——**导出成带 `nodes` 的普通格式是错的**，会直接被识别为非法工作流。

### 16.14 SQLite `ALTER TABLE ADD COLUMN` 不接受「NOT NULL 且无默认值」
- **现象**：给老库的 `gallery` 表加 `owner` 列时，`ALTER TABLE gallery ADD COLUMN owner TEXT NOT NULL` 直接报错，后端起不来。
- **成因**：SQLite 的 `ALTER TABLE ADD COLUMN` **不允许**新增 `NOT NULL` 列却不给 `DEFAULT` —— 已有行没法填值。建表语句里能这么写，ALTER 里不能。
- **思路**：迁移一律写成 `ADD COLUMN owner TEXT NOT NULL DEFAULT ''`。另外**索引也要跟着挪**：老库走不到 `_SCHEMA` 里那句 `CREATE INDEX`，必须把画廊的索引语句从 `_SCHEMA` 移到 `_migrate()` 里、**在 ALTER 之后**执行（本项目为此把索引收进模块级 `_GALLERY_INDEXES` 元组）。新建库与老库两条路径都要能建出同样的索引。
- **配套**：迁移写成幂等的 —— 先 `PRAGMA table_info(gallery)` 查有没有 `owner` 列，没有才 ALTER。反复启动不出错。

### 16.15 删附件前必须查「幸存引用」，否则会误删共享图
- **现象**：删掉一条带图消息，结果另一条**没被选中**的消息里的图也跟着挂了（文件没了，只剩缩略图或直接 404）。
- **成因**：同一张图可能被多条消息引用（转发、重新发送、同图配不同文字）。若"删消息 = 删它的图片文件"直连，就会把还在被引用的文件删掉。
- **思路**：删文件前先查一次 `list_messages_by_image(orig, exclude_ids=本次删除的 id 集合)`：
  - 还有幸存消息引用 → **只删消息记录，保留文件**（用户对此已明确认可："有引用就删"）
  - 再无引用 → 才删画廊收藏（连带照片记忆）与磁盘上的 orig / thumb
- **教训**：凡是"跟着记录一起删资源"的逻辑，都要先问一句"这份资源是否被别的记录共享"，再决定动不动手。

### 16.16 陈旧的级联键：老数据里 `message_id` 存的是序号不是主键
- **现象**：按 `message_id` 级联清理画廊时，老记录匹配不上 —— 早先存进去的图中 `message_id` 是消息的界面序号（`"3"`），而库里 `messages.id` 是 `m-<hex>`。
- **成因**：早期实现直接把前端列表下标当成消息 id 传给了画廊。前端修了（`ChatMessage.dbId` = `StoredMessage.id`），但**存量数据不会自己变**。
- **思路**：级联匹配用**双条件** —— `message_id = <新主键>` **或** `orig = <该消息的图片 URL>`。两条都能命中，老数据照删，不必写数据迁移脚本。
- **教训**：改「引用键」这类标识时，要么一次性迁移存量，要么让新逻辑对新旧两种键都成立 —— 本项目选了后者（更省事，也更能容错）。
